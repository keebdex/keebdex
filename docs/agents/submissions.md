# Community Submission Workflows

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

Signed-in users can propose artisan colorways, keyset kits, and keyboard variants; staff review them before they become public. Every domain uses the same pieces:

- **Routes**: create at `/{domain}/submissions/submit`, review at `/{domain}/submissions` (`artisan`, `keyset`, `keyboard`), both linked from the module's sidebar section for signed-in users. Public create/contribute buttons route to the submit page; standalone modals are only for admin CRUD and sub-entity quick edits. Detail-page _Add …_ links (_Add Colorway_, _Add Kit_, _Add Release_, _Add Variant_, the labels editors see too) pass the query params in "Direct links and response contracts".
- **UI**: review pages are `UTable`s with a status filter (`statusOptions` / `statusColorMap` from `app/utils/index.ts`), scoped to the submitter or to staff for the relevant assignment: artisan lists one row per colorway, keyset and keyboard one expandable row per parent (see "Review flow").
- **Image sizes**: `SharedImageDimensions` shows an image's original `width × height`. `variant="badge"` (default) fills the _Size_ column of every review table (file size and format in its tooltip; `warning` with an alert icon when the longer side is under `LOW_RESOLUTION_IMAGE_SIZE`, 512 px; `-` without an image); `variant="help"` is the muted help text under the image upload of the submission forms, turning into a warning for low-resolution images. Those forms upload through `SharedImageUpload` (`v-model` the picked file, `v-model:src` the image URL): it previews the current image with Replace and Remove buttons (the picked file from memory while it uploads), and shows the dropzone only when there is no image or it fails to load. The form still uploads the file in its own watcher; Remove clears a failed upload so saving is no longer blocked. `getImageInfo(src)` (`app/utils/image-info.ts`, cached per URL, client-only) reads Cloudflare Images originals from the `format=json` flexible variant (CORS-enabled, about 100 bytes, browser-cached for 2 days, though it may count as a delivered image) and falls back to loading the image for other sources. The reject quick replies (`app/utils/review-notes.ts`) include a note asking for a clear, higher-resolution photo.
- **Shared client pieces** (extend these instead of copying per domain):
  - `app/composables/useSubmissionWizard.ts`: `useSubmissionReview` (review status, `canSave`/`canDelete`), `useStepValidation`, `useRepeatableItems` (keyed colorways/kits/variants, `toPayload` strips `_key`). `validateEach` lives in `app/utils/schemas/common.ts`; `pickKeys` in `app/utils/index.ts` hydrates form models.
  - `app/composables/useSubmissionWizardActions.ts`: stepper navigation, review loading and landing step, image-upload tracking, and the submit/save/approve/delete handlers. It returns a reactive object bound to the wizard's `UStepper` (`ref="stepper"`, `v-model="wizard.active"`) and to `SharedSubmissionWizardFooter`. Repeatable cards render through `SharedSubmissionItemList`.
  - `app/composables/useSubmissionReviewQueue.ts` backs the review pages (filter, pagination, row moderation/delete, editor modal; `grouping` adds expand-all, Approve/Reject All, and Delete All), with the `SharedSubmission*` toolbar, pagination, row-action, and bulk-action components.
- **Pending review counts**: staff see what waits for them as badges, never as notifications: on each module's sidebar _Submissions_ link (submissions plus edits, `9+` cap) and on the New / Edits tabs. `GET /api/submissions/pending-counts` (staff only) → `{ artisan|keyboard|keyset: { submissions, edits } }` counts the Pending leaves of their scope like the New tab's Pending filter (kits and variants one by one, through `countGroupedPending`) and the Pending suggestions RLS shows them, minus their own. `usePendingReviews()` holds them; `plugins/pending-reviews.client.ts` loads them for moderators and on tab focus, and both review queues reload them after every action.
- **Status model**: `review_status` (`Pending` / `Approved` / `Rejected`, plus `submitted_by`, `verified_at`, `verified_by`) lives on every submittable table, makers, profiles, and brands included (`20261026000300_catalog_parent_submissions`). A `null` status means a record added directly by staff; it is implicitly approved and never appears in review queues.

| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Artisan  | Maker → Sculpt → Colorway; `POST /api/makers/[maker]` for a new maker, then the sculpt and colorway create APIs                                                        | Colorway (`GET /api/submissions/artisan`) with its sculpt and maker                                 | Maker (0) / Sculpt (1) while Pending/Rejected, else Colorway (2)            |

## Create flow

- Picking an existing, published (null/Approved) sculpt/keyset/keyboard lets any signed-in user add colorways, kits, or releases/variants to it without creating or re-moderating the parent. The proposal is stored `Pending` and is visible only to its submitter and staff.
- Proposing a new parent (or a new maker, profile, or brand above it) creates it first (`Pending`, owned by the submitter), which satisfies the RLS ownership needed for the child inserts that follow. The wizard calls the existing single-entity endpoints sequentially, parent to child; do not describe these multi-write flows as atomic.

## Review flow

- Artisan review rows are single colorways with their maker and sculpt. Keyset and keyboard review are grouped by parent: `GET /api/submissions/keyset` returns `{ data: [{ profile_keyset_id, keyset, kits }], count }` and `GET /api/submissions/keyboard` returns `{ data: [{ brand_keyboard_slug, keyboard, variants }], count }`, where `count` and `page`/`size` refer to groups (ordered by their newest matching leaf) and each group holds every leaf of that parent matching the status filter. Each group is an expandable `UTable` row (expanded state keyed by the parent key via `getRowId`) with a nested leaf table.
- Row actions: Edit (the review wizard with `mode="review"` and `:submission`), moderator-only Approve/Reject (each hidden when the row already has that status; Reject asks for a note in `SharedNoteModal`), and Delete (moderators, or the submitter while the row is Pending/Rejected) behind `SharedConfirmModal`. Group actions: moderator-only Approve All / Reject All for the group's `Pending` leaves and Delete All for its `Rejected` leaves the user may delete, behind `SharedConfirmModal` (`confirmColor` sets the confirm button color), except Reject All, which collects the note in `SharedNoteModal`. Bulk actions send each leaf sequentially to its endpoint (POST to moderate, DELETE to `${leafUrl}/${id}`) so the parent cascade sees every prior result. Toasts name the row and use the `approve` / `reject` / `delete` actions of `successToast`.
- The wizard edits exactly one leaf. Parent levels (sculpt, keyset, keyboard, release) are editable only while under review (Pending/Rejected; a status-less release saved before releases carried their own status follows its Pending keyboard) and render as locked summaries once published. Footer actions (`SharedSubmissionWizardFooter`): Back, Save Changes (submitter), Save & Approve (moderator), Delete.
- Save & Approve saves each parent still under review (keyboard → release) and then the leaf with `action: 'approve'`; approval of the parents rides on the leaf save. Row Approve/Reject post `{ id, action }` (plus the required `note` when rejecting) to the leaf's existing endpoint (save endpoints normalize only the keys present, so a sparse body never blanks other columns); there are no `/api/submissions/{domain}/[id]` endpoints, only the three list endpoints and the two create endpoints above.
- Server-side cascade (`cascadeSculptReview`, `cascadeKeysetReview`, `cascadeKeyboardReview`, sharing `resolveParentReview`): approving a leaf approves its Pending/Rejected parents (status-less sibling kits, or other status-less releases and all status-less variants of the keyboard, are first set to `Pending` under the parent's submitter so they stay in the queue instead of being published unreviewed); rejecting a leaf rejects a Pending parent only once none of its children is still alive. Each cascade then resolves the maker, profile, or brand above the page the same way (`cascadeOwnerReview`, keyed by `ownerKeyOf(pageKey)`; its status-less pages become Pending first). Deleting the last leaf of a parent under review deletes that parent (variant → release → keyboard), and then the maker, profile, or brand under review left with no pages (`deleteOwnerIfEmpty`), so no orphan Pending parents remain.
- A submitter editing their own `Rejected` leaf/parent resets it to `Pending` (server-side), and the page switches its filter to Pending via `onSuccess({ resubmitted })`. Resubmitting a kit or colorway also resubmits its `Rejected` keyset or sculpt (`resubmitRejectedParent`) and profile or maker (`resubmitRejectedOwner`); keyboard and release parents are resubmitted by their own saves, which the review wizard sends before the variant.

## Shared server contract (`server/utils/child-submissions.ts`, `server/utils/submission-queue.ts`)

- Kit, release, variant, and colorway endpoints call `getChildSubmissionContext(event, domain, parentKey)` (parent keys: `profile_keyset_id`, `brand_keyboard_slug`, `maker_sculpt_id`). Client moderation fields are always stripped (`pickTableFields(table, body, MODERATION_FIELDS)`) and re-applied by `attribute()`: official parent + staff → `Approved` with `verified_*`; otherwise `Pending` owned by `auth.uid()`. Kits, releases, variants, and colorways always carry their own status and submitter, also under the submitter's own Pending parent, so each is reviewed and credited on its own (releases since `20261027000200_release_review_status`, which moved the status-less releases of keyboards under review to the keyboard's status and submitter).
- Staff may send `action: 'approve' | 'reject'` (`getModerationOverride`, built on `getReviewPatch`); non-staff get 403. New records get their moderation columns from `getSubmissionAttribution(isStaff, userId)`; resubmission after rejection uses `getOwnResubmission()` / `getResubmissionPatch()`.
- **Page saves** (`POST /api/keysets/[profile]/[keyset]`, `/api/keyboards/[brand]/[keyboard]`, `/api/makers/[maker]/sculpts/[sculpt]`) take moderation fields from nobody: `getPageSaveModeration` strips them and sets them itself. A create is attributed like any submission (`getSubmissionAttribution`); an edit keeps them, except that the submitter's own `Rejected` row is resubmitted as `Pending`, and staff changing the Review Status (the keyset form's field, or the status a wizard echoes) review it: `Approved`/`Rejected` write `verified_*` through `getReviewPatch`, `Pending` only the status. When staff approve a parent still under review that way, `getPageSaveModeration` first sets its status-less `children` (kits, or releases and variants) to `Pending` from the same read of the page, so only the kit/variant actually reviewed gets approved.
- **Owner saves**: makers, profiles, and brands go through `saveOwnerSubmission` (`POST /api/makers/[maker]`, `/api/profiles/[profile]`, `/api/keyboards/brands/[brand]`, keyed by the route param): staff of the key (admins and editors without assignments) add published rows with no status, everyone else proposes a `Pending` one; moderation fields never come from the body, a submitter's own `Rejected` row goes back to `Pending`, and a key taken by a row the caller cannot see is a 409. A body whose key differs from the route renames the record, only while it is Pending or Rejected (see the owner-key rule in AGENTS.md); the review wizards send it last (`owner.rename()`, after the pages below were saved under the current key) and then post the review action to the leaf's new address. Non-staff saves drop the columns edit suggestions protect (a maker's Google Doc settings and flags, logo inversion), and `guard_owner_staff_fields()` rejects them in the database too, so a proposal can't carry `document_ids` that catalog-sync would import once approved. New keys must look like a slug (`urlSlugify`, no `/`), and `record_revision()` moves staff assignments only when a published record's key changes, so a proposal keyed like someone's assignment can't move it.
- Child saves and deletes go through `updateChildSubmission` (resubmission + 403 when RLS refuses), `resubmitRejectedParent`, `deleteChildSubmission`, and `deleteParentIfEmpty`. Updates and deletes must check the affected row count: RLS filters silently, so return a 403 with a message when nothing changed.
- List endpoints use `getReviewQueueContext` (actor, assignment scope, page/size, whitelisted status via `parseReviewStatus`); the grouped keyset and keyboard queues are both `listGroupedSubmissions` configurations (`KEYSET_QUEUE`, `KEYBOARD_QUEUE`), sharing `groupedChildRequest` with `countGroupedPending`. `inFilter` quotes values inside PostgREST `or()` filters.
- Release and variant saves normalize numbers, optional strings, and material arrays with `normalizeFields` (`server/utils/index.ts`); empty arrays are stored as `null`.
- Public reads show only published records; records under review are reachable only through the review queue. `GET /api/keysets/[profile]/[keyset]` filters its kits server-side. `GET /api/keyboards/[brand]/[keyboard]` and the sculpt endpoint still return records under review because the wizards read them (the keyboard page filters releases and variants client-side; Pending sculpts stay listed on maker pages).
- Sculpt proposals live in `artisan_sculpts` and have no separate queue.

## Database & RLS conventions for submissions

- A table that supports submissions needs the four control columns, added through a migration.
- Target RLS: public reads Approved/null rows; submitters read their own Pending/Rejected rows; authorized staff read and manage their scope. Non-staff inserts must be `Pending`, attributed to `auth.uid()`, with null `verified_*`; only staff may insert null/approved rows or change moderation fields. Submitters update their rows while `Pending` (also `Rejected`, which resubmits as `Pending`) and delete while `Pending`/`Rejected`, never `Approved` or `null`.
- Child tables combine the parent's state (via `exists` subqueries) with their own: community inserts need an official parent, or the submitter's own Pending parent (kits and releases → own Pending keyset or keyboard; variants → own Pending keyboard plus an official release or own Pending release). Staff scope comes from `can_manage` (keyset: `profile_keyset_id` for keysets, kits, and keyset colors; keyboard: the parent's `brand_slug`, not the child's column; artisan: `maker_id`). Never broaden child INSERT permissions without controlling visibility and moderation. Verify the deployed policies; local migration drafts are not proof they are applied.

## Auto-approve rule for staff submissions

- When the actor is staff for the relevant assignment (`canManageAnyAssignment(profile) && canManageAssignment(profile, assignment)`: `brand_slug`, `profile_keyset_id`, `maker_id`), creates through the shared endpoints (`/api/submissions/*`, and the kit/release/variant/colorway create endpoints used by admin and community forms) are written as `Approved` with `verified_by = user.sub` and `verified_at = new Date().toISOString()` in the same insert. Non-staff always get `Pending` with null `verified_*`.
- `submitted_by` defaults to `auth.uid()` on every submittable table (`20261027000100_backfill_submitted_by`), so every insert by a signed-in user names them, staff included, whichever path it takes (`saveOwnerSubmission` relies on it for the status-less makers, profiles, and brands staff add); the leaderboard counts by it. Syncs and the SQL editor have no `auth.uid()` and leave it null. The app still sets it explicitly through `getSubmissionAttribution`, and no edit changes it.

## Delete cascade rule for submissions

- Delete children before the parent while parent-scoped RLS still applies, using the per-item delete endpoints (never a published parent): keyboard variants → releases → keyboard → brand; keyset kits → keyset → profile; artisan colorways → sculpt → maker (owners only while under review). Check every delete result instead of relying on `ON DELETE CASCADE`.
- Delete rights follow the RLS rule above: authorized staff, or the owner of a `Pending`/`Rejected` submission, never of an `Approved` or `null` record.

## Nested submission wizards

- Wizards live in `app/components/{artisan,keyset,keyboard}/modal/SubmissionWizard.vue`, use `UStepper`, and embed the same atomic forms in create and review. Per-domain steps and review behavior are in the table above.
- Every step above the reviewed item renders through `SharedSubmissionEntityStep` (`v-model:selected` / `v-model:entity-mode`, `tabs` when there is something to pick, `options` or a `select` slot such as the keyset search, the entity's form in the default slot; in review the form while `under-review`, else the published `name` and `to`).
- Step 1 (Maker/Profile/Brand) is driven by `useSubmissionOwner(domain, selected, onNew)` (its `stepProps` bind to the step; `onNew` switches the next step to new): an existing one (published, plus the caller's own proposals through `?own=1`) or a new one proposed in `MakerForm` (`suggest`), `KeysetModalProfileForm`, or `BrandForm`, created first on submit by `ensure()` (its key is the form's slug or `urlSlugify(name)`). A proposed owner has nothing to pick under it. In review it is locked once published and shows its form again while under review (`load`, `save` before the rest).
- In create mode, the other reusable intermediate entities (Sculpt/Keyset/Keyboard/Release) also use a step-level `UTabs` toggle between `'existing'` and `'new'`, never a toggle inside an atomic form. Render it only when options are loaded and non-empty. Treat only a successful empty response as evidence for proposing a new entity; never discard a preselected existing entity because options are empty, paginated, pending, or failed.
- Exception: the keyset step does not preload keysets. Its picker searches as the user types through `useGuardedSearch('/api/search', { term, module: 'keyset' })` (like `KeyboardForm`'s original-keyboard picker), keeping only results whose `to` is under the selected profile and using `to` minus `/keyset/` as the `profile_keyset_id`. The Existing/New toggle is therefore always shown in create mode and never auto-switches to New. The selected option is kept in `selectedKeyset` (a direct link resolves its label via `GET /api/keysets/[profile]/[keyset]`) so its label survives new searches.
- Create mode supports repeatable Colorways/Kits/Variants; review edits exactly one colorway/kit/variant (the table row) with no Add/Remove controls.
- Validate each step before advancing and validate the applicable entity/child data before saving or approving.
- Selection context belongs in computed `StepperItem.description` values using selected option labels or in-progress entity names. Do not add redundant "Selected: ..." paragraphs next to pickers or repeat context inside step slots.

## Direct links and response contracts

- Detail-page links pass `maker`/`sculpt`, `profile`/`keyset`, or `brand`/`keyboard`/`release` query parameters. Jump to Colorway/Kit/Release/Variant as appropriate; derive missing profile/brand from the child's composite slug when available.
- Parent-change watchers reset dependent selections only on actual changes, never with `{ immediate: true }`. Use a separate immediate watcher for initial field synchronization (e.g. `keyset.profile_id`).
- `GET /api/keysets` returns `keysets`, not `data`. Preserve `existingKeyset.id` from direct links and submit kits through its existing-keyset endpoint rather than creating a blank keyset.
- `GET /api/makers/[maker]` returns `sculpts` keyed by ID; unwrap with `Object.values(...)` before mapping options.
- A direct "Add Release" link with a keyboard but no release selects `'new'` and hides the release toggle. Variant forms use a synthetic release option with ID `'draft'`, matching new variants' `release_id`; resolve the real release ID only at submit time.
- Embedded `KeysetForm` must bind `v-model:date-range` separately and convert its CalendarDate values to ISO `start_date`/`end_date` on submit. It hides its Profile field (step 1 picks the profile, a proposed one included, and the wizard syncs `profile_id`); with `colors` (create mode) it shows _Colors_, which the wizard saves after creating the keyset (`POST /api/keysets/[profile]/[keyset]/colors`). Status and Review Status remain visible; Review Status is disabled for non-moderators, read directly from the user store.
