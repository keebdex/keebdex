# Changelog and Releases

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

- **Files**: `content/changelog/` holds one Markdown file per release (`v<version>.md`, frontmatter `version`, `title`, `date`, optional `prerelease` and `authors`: GitHub usernames, or `{ name, icon (with optional `color`) | avatar, to }` for co-authors without one, such as Claude), plus `unreleased.md` (title only, `Unreleased`) with the notes for the next release. `/changelog` shows each entry's `title` (the release name) as its heading and one badge: `v<version>` for releases and _Pre-release_ for pre-releases. `unreleased.md` comes first because those changes are already live: its heading is _Since v<latest version>_ (its frontmatter `title` is not shown) and its badge is the running build, `buildId` from `nuxt.config.ts` (`v<version>+<commit>`). The page opens with `SharedInfoHero` (the info-page convention in `docs/agents/catalog-pages.md`), then _Releases_: every release on one horizontal `UTimeline` (`value-key="tag"`, newest first, only the release being read marked: the completed state is styled like a pending one), each item a fixed width in a sideways-scrolling, snapping line with its name (a button) and version, the release's Nuxt Content `description` (its first paragraph) clamped to two lines, and its date (_Live now_ for the unreleased notes). The arrows on the dots' line, right of it from `sm` (phones swipe), scroll the line a screen at a time and turn off at either end; the _Releases_ heading is for screen readers only, so the notes start high. Below it, one release at a time (`v-show`, so every release stays in the HTML for search engines): its title (`h2`, the `release-<version>` anchor), and its notes, in a `UPage` (`as="article"`, the notes over 7 of its 10 columns) whose `#right` is a `UPageAside` (shown below the notes on smaller screens instead of hidden, and stuck to the top of the panel body, which is the scroller): _In this release_ (from `lg` only), its `###` sections from `body.toc` with how many changes each lists (the `ul` after the heading in the minimark body), then its badge, date, and authors. The heading ids repeat in every release and the hash names the release, so those links scroll to the heading inside the release being read (`scrollToSection`) instead of changing the hash. The release being read follows the URL hash both ways (a direct link opens that release, and the line scrolls it into view on load; picking one replaces the hash), and a release picked after scrolling down a long one scrolls its title back into view. The notes keep Nuxt UI's prose style. This is the Nuxt Content `changelog` collection (`content.config.ts`). Edit a released version here, not on GitHub. On Cloudflare, Nuxt Content stores the collection in D1 through a binding named `DB` (the `keebdex-db` database); local builds use SQLite.
- **Cutting a release**: run `bun run release <version> "<name>" [--prerelease]` (turns `unreleased.md` into `content/changelog/v<version>.md` with version, name, and date, keeps its `authors` or credits the `gh` user when it has none, and bumps `package.json`), commit it as `chore(release): v<version>`, push, then run `bun run release:publish <version>`, which creates the GitHub release (tag `<version>`, title `v<version> - <name>`, the format of every existing release) from that file, or updates it when it already exists. GitHub releases are copies of the files, never the source.

## Release notes

Release notes are read by collectors, not developers. Keep every release in the same shape:

- **Summary**: one short paragraph that opens with a bold phrase tied to the release name (e.g. "Throw the **doors open** —" for _Open Doors_), then names the two or three biggest changes.
- **Sections**, in this order and only when they have entries: `### ✨ What's New`, `### 🐛 Bug Fixes`, `### 🚀 Improvements`, then `### ⚠️ Breaking Changes` for changes users notice (renamed pages, moved addresses). Never write "None".
- **Entries**: a full, natural sentence each (two when needed), describing what users see or can now do and why it helps, in the present tense, ending with a period. Avoid clipped fragments that read abruptly ("Images load faster."); say enough to give context ("Grids load images sized for your screen, so pages load faster, especially on phones."). Bold the feature name when it leads the entry; italicize UI labels (_Save_, _Group Buys_).
- **Length**: there is no fixed number of entries; a big release can be long. What must not happen is overlap: merge entries that describe the same feature or area (e.g. several keyset page fixes) into one, and describe a large change once, in What's New, instead of again under Improvements.
- **Leave out** internal work users never see: composables, refactors, table or column names, lint and dependency updates, RLS or API fixes without a visible symptom. Do not list every label, route, or option; name the feature and its benefit.
- **Names**: release names are short and evocative, two or three words without a leading article, matching the theme of the release (_First Keystroke_, _Keyboard Era_, _Aurora Borealis_, _Open Doors_).
- **Authors**: keep `anhthang` first; add Claude as a co-author (`name: Claude`, `icon: simple-icons:claude`, `color: '#D97757'`, `to: https://claude.com/claude-code`) when Claude worked on the release.
- Before cutting a release, reread `unreleased.md` against these rules: entries added change by change tend to grow too long and to repeat each other.
