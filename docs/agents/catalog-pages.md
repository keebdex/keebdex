# Catalog Pages

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

The public catalog pages: the home page, the catalog lists (makers, brands, profiles, group buys, and the maker, brand, and profile pages), the keyset pages, and the keyset, keyboard, and sculpt detail pages, plus the hero, cards, and header actions the detail pages share. `/collection` follows the list layout too. Every page here follows "Page header layers" below: the navbar says where the page is, the `UPageHeader` names it.

## Page header layers

Each layer of a page's top answers one question, so no name is shown twice:

- **Navbar** (`UDashboardNavbar`): where the page is. A module's page shows the module as its title. A page inside it (owner, detail, collection) uses `SharedBreadcrumbNavbar` with its `breadcrumbs`: the `UBreadcrumb` on desktop and tablets, and on phones a back button to the last item with a link, labeled with its name (icon-only beside the page's title when the trail ends with the page itself, as on manual sort); `#right` passes through. The trail ends at the parent page; the component sets `active: false` on every linked item, so the parent is neither highlighted nor `aria-current` and pages pass plain items. Content pages put no actions here.
- **Sidebar toggle**: `app/app.config.ts` sets `toggleSide: 'right'` as the default variant of `dashboardNavbar` and `dashboardSidebar` (Nuxt UI reads props from `defaultVariants`), so no page passes `toggle-side`, and below `lg` the menu button sits on the right of every page, after the page's own buttons, and the left holds the title or the back button. The sidebar matches: below `lg` it slides in from the right (`:menu="{ side: 'right' }"` in `app/layouts/default.vue`) with its close button on the right (the same default).
- **Toolbar** (`UDashboardToolbar`): how to view the page: view switchers, tabs, search, filters.
- **Page header** (`UPageHeader`, first in the body): what the page is and what can be done on it: the title, a description, and every page action in `#links`. No `headline` repeating the module.

Tool pages (`/admin/**`, submissions, notifications, recent changes, leaderboard, the settings shell, the Wishlist Image builder, a collection's manual sort) have no page header: the navbar holds the title and the page's actions in `#right`, with a filter there only where the toolbar has no room (Recent Changes' _Changed by_ in its narrow list panel).

## Detail page conventions

- **Cards**: variant cards, keyset kit cards, and the colorway cards of the sculpt page and `/artisan/search` are one `SharedCatalogCard`: the image (`aspect` `video` with a `fallback` image, or `square` with an icon placeholder), the name with a formatted `price` (`price-struck` when cancelled), a two-line description, a `badges` slot over the image, Add Photo (for suggesters, emits `suggest` like Edit), and a footer with `footer-start` (`SharedSaveToCollection`, always labeled _Save_ or _Move_, or a kit's units) on the left and, on the right, the page's own ghost icon buttons (`footer-end`) then Edit / History / Delete. The footer wraps the icons to a second row on narrow cards.
- **Record actions** (`SharedRecordActions`, wrapped by the card and used directly by headers and release rows): `editable` for staff (edit in place, History, and Delete only where the page binds `@delete`, which `deletable` can still gate, e.g. a release with variants); `suggestable` alone makes Edit suggest; emits `edit`, `suggest`, `history`; `ghost` on cards and release rows, the theme's button style otherwise; `label` names the buttons (_Edit Release_). The icons are fixed (`edit-01`, `file-remove`) so every module shows the same ones. Its tooltips render only in the browser (`ClientOnly`, bare buttons as fallback), so card grids don't render a tooltip tree per button on the server.
- **Missing records**: the maker, sculpt, profile, keyset, brand, and keyboard pages call `throwIfNotFound(error.value)` (`app/utils/not-found.ts`) after their awaited `useAsyncData`, so a missing record (or one under review, since the server renders as a guest) answers 404 through `app/error.vue`. Collection pages do not: a private collection would 404 for its owner on a direct load.
- **Detail hero**: the keyboard, keyset, and sculpt pages open with `SharedDetailHero`: a `#media` slot (the keyboard's photo carousel, the keyset's cover; the sculpt page has none) beside the default slot, taking 3/5 of the row from `lg` and half from `2xl`, sticky beside taller details; without media the details take the whole row. Inside, a `UPageHeader` with `detailPageHeaderUi(withMedia)` (`app/utils/index.ts`: no border or padding, title at the start, actions beside the title except under it from `lg` to `xl` beside media, where the column is too narrow for both) and the page's specs as a `SharedSpecList` with `layout="rows"`. Every later section opens with a section-sized `UPageHeader` (`detailSectionHeaderAs` / `detailSectionHeaderUi`: an h2 title, no border or padding, actions beside the title) and only `pt-4` above it (no border: the spec rows' own border already closes the hero, and a second line with space on both sides read as empty).
- **Add buttons**: Add Release, Add Variant, Add Kit, and Add Colorway bind `submissionTarget(editable, onClick, module, query)` (`app/utils/index.ts`): staff open the form in place, everyone else goes to `/<module>/submissions/submit` with `query` preselected.
- **Headers**: page headers (maker, sculpt, brand, keyboard, keyset profile, and keyset pages) use `SharedRecordActions` too (only the sculpt page binds `@delete`). Every other header action is icon-only with a tooltip and an `aria-label` (Sort, Pins), except the primary Add button (Add Sculpt, Add Colorway, Add Keyboard, Add Release, Add Keyset) and _Save_, which keep their labels. Order: the labeled primary action (Add, or _Save_ on the keyset page), then Edit / History / Delete, then the page's own tools (Sort Releases, Customize Pins, Add Cover). List controls are not header actions: the sculpt page's sort select sits in its _Colorways_ section header.
- **Modals**: the edit forms and `SharedRevisionHistory` (opened through its `show()`) sit with the page's other staff modals, one form per record type per page. Pages that delete records from cards share one `SharedConfirmModal` through `useConfirmDelete(onDeleted)` (`target`, `deleting`, `open(entity, name, url, then?)`, where `then` replaces `onDeleted` for that call, e.g. to leave the sculpt page after deleting the sculpt, `confirm`) instead of a confirm modal per card.

## Catalog lists

- **List pages** (`/artisan/maker`, `/keyboard/brand`, `/keyset`, `/keyset/group-buy`, `/collection`): the navbar title is the module (_Artisans_, _Keyboards_, _Keysets_, _Collection_; the group buy and color tabs as its toolbar); the body opens with a `UPageHeader` through `listingPageHeaderUi` (`app/utils/index.ts`: no headline, since the navbar names the module, a large title, a sentence, and the page's actions in `#links`: the labeled Add button, then Customize Pins icon-only). Lists show no counts and have no filter for now.
- **Section headers** appear only where they hold an action (Add Kit, Add Colors) or name a group (catalogs on `/collection`); a list with neither follows the header directly (`pt-4`).
- **Pins**: signed-in users pin makers and keyboard brands on their list pages, then, on a pinned maker's or brand's page, its sculpts or keyboards. They live in `users.pins` (jsonb), grouped by catalog: `{ artisan: { <maker_id>: [<sculpt_id>] }, keyboard: { <brand slug>: [<keyboard slug>] } }`, so a company in both catalogs (GSK) has one entry in each. The user store reads them through the `pinnedMakers` and `pinnedBrands` getters and saves them with `savePinnedOwners(module, ids)` and `savePinnedChildren(module, owner, ids)`, which change one catalog's group only. Once anything is pinned, `splitPinned` (`app/utils/index.ts`) splits the list into _Pinned_ and _Others_, each under a `SharedPinGroupLabel` eyebrow (the pinned one in the primary color with `PINNED_ICON`); Customize Pins opens `SharedPinForm` in the same order, pinned first, with logos for makers and brands. Pins have no limit, and cards carry no pin of their own.
- **Logo cards**: makers, brands, and keyset manufacturers are `SharedKeebLogoCard`s in one `artisanGridClass` grid: the logo on a square tile, inset by a share of its width (`p-[14%]`, so wide cells keep the same margin), and the name, nothing else; without `to` it is not a link (a manufacturer with several profiles, as its picker's trigger).
- **Profiles** (`/keyset`): one card per manufacturer (grouped with `groupBy` by `keysetProfileLogoKey`: the `manufacturer_id`, or the profile alone without one; both sorted by name), since sets are named after the maker and the profile (GMK CYL) and one maker makes several profiles (GMK: CYL and MTNU). A manufacturer with one profile links the whole card to `/keyset/<profile_id>`; one with several is the trigger of its own `UModal` (its name as the title) with a plain CSS grid (not `UPageGrid`, whose columns follow the screen) of subtle `UPageCard`s (two columns, three from three profiles; `p-0.5` so the modal body's scroll edge does not clip their rings), one per profile: the profile's name and, when it differs, its keycap family (_CYL_, _Cherry_). The rows come from `useKeysetProfiles().profiles` (`profile_id`, `name`, `profile`, `manufacturer`, `manufacturer_id`), the only data its `transform` keeps: `groupedProfiles` and `manufacturers` are built from them in the browser, so keyset pages carry the names once.
- **Owner pages** (maker, brand, keyset profile): open with `SharedOwnerHero`, a `SharedDetailHero` without media: the logo beside the name as the `UPageHeader` title, the actions in its `#actions` slot (Add Sculpt / Keyboard / Keyset through `submissionTarget`, then `SharedRecordActions`, then Customize Pins on a pinned maker), the bio as the description, the specs as `SharedSpecList` rows (maker: Founded; profile: Profile, Manufacturer; brands have none; no country and no counts), and the external links (`ownerLinks(record)`, then the maker's ArtisanCollector and Catalogue) as labeled buttons under them. There is no _Info_ drawer. On phones (`$device.isMobile`) everything under the name folds into a `detailsLabel` `UCollapsible` (_Maker Details_), closed by default, like the sculpt page. The owner's list follows: sculpts as square `SharedCatalogCard`s with `to` in `artisanGridClass` (`/artisan.png` fallback, its collection as the description), keyboards as video-cover cards in the default `UPageGrid` (`/keyboard.png`, the description, the form factor as a badge), keysets through `KeysetGrid`.
- **`KeysetGrid`** (shared by the profile page and the group buy tabs, which own their panels): video-cover `SharedCatalogCard`s (`/keyset.png` fallback), the name (with the profile on the group buy tabs), the group buy dates or the IC date, a phase badge for every phase but Confirmed (most of the catalog), or the `groupBuyCountdown` badge with `countdown` (the Live tab), and _Save_; an `#empty` slot and the pagination (`update:page`).
- **Collection** (`/collection`, signed-in): a section per catalog of image cards (`UPageCard`, `reverse`, `imageCardContainerClass`), the cover a mosaic of up to four of the collection's photos (`images` from `GET /api/users/:id/collections`, which returns only their URLs). Under the name: _Public_ or _Private_, and on artisan wishlists and sale lists a _Wishlist_ or _For Sale or Trade_ badge (`TRADE_INTENTS` colors and icons). No item count, nothing over the photos. Collection pages (`/collection/<catalog>/[collection]`) lay their items out as `SharedCatalogCard`s (colorways `square`, keysets and keyboards `video`), linking to the item's page (a colorway opens its drawer through `?cid=`), and for the owner _Move_ on the left and ghost icon buttons in `footer-end` (_Edit Listing_ on wishlists and sale lists, _Remove_), with one listing form and one `SharedConfirmModal` per page; the remove dialog's state comes from `useCollectionItem` (`removing`, `confirmRemove(id, label, entity?)`, `confirmRemoval()`). Found or sold caps are `dimmed` with the mark over the photo, priority ones `highlight`ed, and colorways gone from the catalog offer _Clear Outdated_ instead.

## Home

- **Home page** (`app/pages/index.vue`): a column of sections from `app/components/home/`, each opening with `HomeSectionHeader` (a small mono uppercase headline, `eyebrowClass` in `app/utils/index.ts`, in the primary color, the title, a sentence, and its links on the right). `GET /api/statistics` feeds the first three through `useHomeStatistics()` (one `home-statistics` fetch, returning `data` and `catalogCount(key)`) with only what the page shows: the eight makers with the most new colorways in the last day (`makers`), the five live group buys closing first (`keysets`) with `liveCount`, the newest photographed colorways, one per sculpt (`showcase`, 12), and the published catalog sizes (`catalog`). The colorway count is the planner's estimate, since an exact count can time out, so `catalogCount` shows it as a round figure through `formatEstimate` (_68,000+_); a failed count is `null` and `catalogCount` gives `''`.
  - `HomeHero`: a horizontal `UPageHero` (its container without gutters, since the page sets them) with the search button (`KeebSearch` palette), _Start Collecting_ (_My Collection_ when signed in, to `/collection`, which shows guests its sign-in page), _Why Choose Keebdex?_, and the catalog sizes. Beside it from `lg`, `HomeKeycapMosaic` lays the showcase out as three staggered rows of keycaps (a 19-column quarter-unit grid), each photo a key that presses down on hover and opens the colorway's drawer; it shows from eight photos.
  - `HomeHappeningNow` (hidden when both lists are empty): _New from Makers_ and _Closing Soon_ (either takes the row alone), each live group buy with its `groupBuyCountdown` (`app/utils/keyset-status.ts`: a days-left badge, warning-colored in the last three days, and the share of the group buy elapsed as a progress bar). Days are UTC dates, as in `liveGroupBuys`.
  - `HomeBrowseDex`: one card per catalog.
  - `HomeTopContributors` (hidden while nobody has contributed this month): this month's top three on `LeaderboardPodium` beside ranks 4–6 as compact `LeaderboardRow`s and the signed-in user's own rank when they are not among them; the board renders on the server and the user's rank loads in the browser.
  - `HomeShoutouts`: featured `ShoutoutCard`s (shared with `/shoutouts`), bleeding to the panel's edges, in one row or two opposite rows from six. They go through `HomeMarquee`, which scrolls only when there are more than `max` items (a few repeated items read as duplicates) and otherwise centers them at the `itemClass` width, keeping cards one width; its marquee sets `ui.content: 'w-auto'`, since `UMarquee`'s `w-full justify-around` spreads short lists apart, and fades its edges with a mask instead of `UMarquee`'s overlay, which sits above the cards and covers the one paused under the pointer.
  - `HomeArtisanGuides` (ArtisanCollector's guides, opening in a new tab) and `HomeContribute` (a closing `UPageCTA`, one link per submission wizard).
  - Motion is CSS only (`app/assets/main.css`) and off under `prefers-reduced-motion`: the hero's parts rise in on load (`home-rise`, staggered through `[--i:n]` in its `ui`), the mosaic's keys drop in one after another (`home-key` with `--i`), and every section after the hero fades up as it scrolls into view (`home-reveal` on its root in `index.vue`, a scroll-driven `view()` timeline; browsers without one show it still).

## Keysets

- **Keyset pages**: sidebar order is Profiles (`/keyset`), Group Buys (`/keyset/group-buy?status=ic|live`; legacy `/keyset?status=…` redirects, and any other value falls back to `live`), Colors, Submissions. `GET /api/keysets?status=`: `ic` is the Interest Check status, `live` every Confirmed keyset whose `start_date`–`end_date` holds today, through `liveGroupBuys(query)` in `server/utils/index.ts`, which `GET /api/statistics` uses too. `/keyset/[profile]` sends the route param as `profile_id`, since the profile list may not be loaded during SSR. Profile logos are their manufacturer's (`logoUrl(keysetProfileLogoKey(profile))`: the `manufacturer_id`, falling back to the `profile_id`) and always invert in dark mode (no `invertible_logo` column).
- **Keyset status**: `keysets.status` only says whether a set is going ahead (`KEYSET_STATUSES` and `KeysetStatus` in `app/utils/keyset-status.ts`, from the `keyset_status` enum): Interest Check (not decided yet), Confirmed (happening, from group buy to delivery; `DEFAULT_KEYSET_STATUS`, also the column default), or Cancelled; the column is a not-null enum (migration `20261028000000_keyset_status_cleanup`). Never write another status or null; catalog-sync sends none and gets the default. `keysetPhase(keyset)` gives the badge: Live by the same rule (Confirmed and dates hold today), else the status; `keysetPhaseColors` colors Live and Cancelled. `keysetDateLabel(keyset)` is the date a keyset is known by (its group buy window, else `IC <date>`), on keyset cards and in the color drawer. Today is the UTC date (`isoToday`), on the server and in the browser alike.
- **Colors** (`/keyset/color`): a listing page (navbar title _Keysets_, header titled _Color Swatches_, Add Color and Import for staff) with the matching systems as toolbar tabs in the URL (`?system=GMK`, any other value shows all), a search by code or name (debounced, `GET /api/colors` full-text), and a grid of `KeysetColorTile`s (`colorSwatchGridClass`, two to six columns, 48 per page, so rows stay whole): the swatch with its hex in a contrasting color (`isLightColor` in `app/utils/color.ts`), the system and code, the name, and how many keysets use it when any (`?usage=1` adds `keyset_count`, an embedded `keyset_colors(count)`; other callers of `/api/colors` leave it off).
- **Color drawer**: a tile opens `KeysetColorDrawer` through `?color=<id>` (linkable; `useQuerySelection('color')` gives the id, the drawer's `open`, and `select`, and keeps the last id while the drawer slides closed). It shows the tile's data at once (`preview`), then loads `GET /api/colors/[id]` (the color and its published keysets, newest first; 404 for an unknown id, which also covers ids past the `smallint` range) for the specs (system, code, hex, RGB; the name is the description), a copy-hex button, and _Used In_ (keyset rows linking to their pages, under their `keysetDateLabel`). With `manage` (Colors page only), staff edit from the drawer (icon buttons in its header, beside the close button) and admins delete only a color no keyset uses, since `keyset_colors` restricts deleting a color in use. One color form and one `SharedConfirmModal` serve the page.
- **Keyset detail page** (`[profile]/[keyset]/index.vue`): the cover (keyset `img`, else first kit) is hidden when missing or broken, with no placeholder; the header's `#links` hold _Save_ with its label, then Edit and History. The reference links sit under the specs as labeled buttons: _Geekhack_ (only when `url` is a geekhack thread; vendor pages are left out, since they go stale once the group buy ends), _Order Graph_, and _Order History_ (dvorcol's charts, opened in the preview modal). The specs (designer, row sculpt, IC date, timeline, status as a badge) are rows under the header with no heading. Kits and Color Palette have section headers (the color note is the palette's description) with a ghost icon-only Add (Add Kit through `submissionTarget`; Add Colors staff only), and fall back to `UEmpty`. Kit cards show `price`/`qty` when set, units on the left of the footer. The Color Palette uses the Colors page's swatches, smaller (`KeysetColorTile` with `compact`: a 3:2 swatch and smaller text, in `colorPaletteGridClass`, three to eight columns); colors are only added and removed (Remove in the tile's `action` slot), with no per-color history, since color changes are revisions of the keyset. A swatch opens the same `KeysetColorDrawer`, without `manage` and with this keyset left out of its list (`exclude`, titled _Also Used In_). One kit form, one color form, and one `SharedConfirmModal` serve the page; there are no `kit`/`color` sub-pages.
- **Keyset preview modal**: one modal serves kits, cover, and order graph/history; opened from a kit, it shows a looping `UCarousel` of the kits that have an image (swipe, arrows, a position counter; the title and description follow the selected kit). The carousel handles arrow keys only while focused, so the page adds left/right `defineShortcuts` while a kit is shown, skipped when focus is already inside the carousel; `start-index` comes from a separate `kitStart`, since changing it re-initializes Embla.

## Artisans

- **Sculpt page** (`app/pages/artisan/maker/[maker]/[sculpt].vue`): a `SharedDetailHero` without media holds a `UPageHeader`: the sculpt's name alone as its title (the breadcrumb shows the maker and its logo); a _Revision of_ headline link to the sculpt its `is_revision_of` points at, found in `maker_sculpts` from the sculpt response, so no extra request (the sculpts revised from this one are not listed); the story as its description (there is no story drawer); and Add Colorway, then Edit / History / Delete in its `#links`. Under it, `sculptSpecItems` (`app/utils/artisan.ts`) as rows: Profile, Cast, Design (labels from `artisanSculptProfiles` / `artisanSculptCasts` / `artisanSculptDesigns` in `app/utils/schemas/artisan.ts`, shared with `SculptForm`), Release, and Collection, leaving out unset ones, since most sculpts only have a few. On phones (`$device.isMobile`, so SSR matches) the story and specs fold into a _Sculpt Details_ `UCollapsible`, closed by default, so the colorways start on the first screen; it is left out when the sculpt has neither. The _Colorways_ section has the sort select in its header, then the `artisanGridClass` grid of `SharedCatalogCard`s with only the photo and name (details are in the drawer), then the pagination.
- **Colorway drawer**: clicking a colorway opens `ArtisanColorwayDrawer` (one `USlideover` for the page): the colorway and sculpt names as its title and the maker as its description, the square photo (`/artisan.png` when there is none), the description, a _Details_ section (not _Specifications_, since these describe a drop rather than a build) as a three-column grid (`colorwaySpecItems`: Release, Sale Type, Price, Units, Stem, Photo Credit; unset ones show `—`), and _Save_ and _Share Card_ in its footer. _Share Card_ opens the trading card popup (`ArtisanColorwayCard`) over the drawer. `?cid=<colorway_id>` opens the drawer (paging to the colorway first through `selected_colorway_index`), so links from search and collections land on it; closing the drawer drops it from the URL and keeps the colorway shown while it slides out.

## Keyboards

- **Keyboard detail page** (`app/pages/keyboard/brand/[brand]/[keyboard]/index.vue`), laid out as a catalog entry. Releases follow `order` (staff set it through Sort, newest first) and only published (`isApproved` in `suggestions.ts`) releases and variants show.
  - **Catalog entry**: a `SharedDetailHero` with the photos as its media: a looping `UCarousel` (`photos`: every variant with a photo, newest release first, each variant's `img` being its front photo, else its back, worked out once in `releases`; arrows from two slides, inside the slides through the `carousel` theme in `app/app.config.ts`). Only the current slide, its neighbours, and slides already shown render their photo (`slideShown`), so the server builds three images instead of every variant's; each slide's caption opens the variant drawer. A filmstrip (a listbox) follows the carousel both ways: a thumbnail calls `emblaApi.scrollTo`, and the carousel's `@select` sets `activePhoto`, which highlights the thumbnail and scrolls it into view. With no photo, `/keyboard.png` shows instead. Beside it: the brand logo beside the full name as the title, a _Based on_ headline link (`derived_from`), the description (`SharedDescription`, which renders one paragraph per line in a single `space-y-2` root, so classes passed to it apply), and, for signed-in users, Add Release with its label, then `SharedRecordActions`, then Sort. Under it, the design every release shares as `SharedSpecList` rows (`keyboardSpecItems`: Form Factor, Top Case only for `keyboardTopCaseStylesEnabled`, Mount, Typing Angle; `—` when unset). There is no catalog ID or catalog record (production years, counts, verification). Materials, price, and units stay with releases and variants (`keyboards` has no material columns).
  - **Derived Designs**, right under the header and before the history so many releases don't bury it, when other keyboards are based on this one (`derived_keyboards` from `GET /api/keyboards/[brand]/[keyboard]`, each with a `cover_image`): a `UPageGrid` of `UPageCard`s, each only the cover (`cover` preset) and the name, since the section description says what they are. A derived keyboard shows its original only as the header's _Based on_ link (the API returns either the original or the derived list, never both), so there is no original card.
  - **Production History**: the releases as a `UTimeline` (`timelineItems`: a release icon and the release itself for the slots; the indicator and separator are primary through its `ui`, since no item is selected). No year or date shows; the `#title` slot holds the release name with the ghost actions on its right (Add Variant, then `SharedRecordActions`, Delete only once the release has no variants); there is no variant count, and the section header has no description. The `#description` slot (`text-base` through the timeline's `ui`; its color is the page's text through the `timeline` theme in `app/app.config.ts`, since the default muted text would reach the cards, and themes such as Analog Dreams and EVA-01 color muted text apart) holds the rest: the description clamped to three lines (the variant drawer shows it in full), its specs as a `SharedSpecList` (`releaseSpecItems`: Top Case, for form factors that have layouts, as the release's own or, left empty, the keyboard's through `releaseTopCaseStyles`, then materials), then its variants as a `UPageGrid` of `SharedCatalogCard`s (two columns from `lg`, three from `xl`, since the rail narrows it; finish as the description, price, a _Custom Specs_ badge, _Save_; clicking one opens the variant drawer), or _No variants recorded yet_. There is no variant table and no filters.
  - With no published release, `UEmpty` (_Nothing Has Shipped Yet_) replaces the history.
- **`SharedSpecList`** (also on keyset pages and in the variant drawer): `layout` `divide` by default, a row with subtle separators; `grid`, even columns, three once its container is wide enough; or `rows`, one bordered row per spec with the label left and the value right, in one column, two from `@md`, three from `@3xl`; all by container width, `divide` and `grid` two columns when narrow; an item's `badge` replaces its text.
- **Spec inheritance**: specs are set once and inherited downward: the keyboard holds form factor, mount, typing angle, and every layout it supports (`top_case_styles`, for `keyboardTopCaseStylesEnabled` form factors); a release holds year, price and currency, materials, and optionally the subset of layouts it was sold in (`keyboard_releases.top_case_styles`, null for all; `hasTopCaseStyles(keyboard)` says whether the form factor has layouts); a variant leaves each of year, price, currency, and materials empty to take its release's and sets one only where it differs (a price of its own is read in its own currency, else the release's; a special sale, `SPECIAL_SALE_FORMATS` in `app/utils/keyboard.ts`: Giveaway, Commission, Auction, Friends & Family, never takes the release's price, so it shows only its own, and `VariantForm` then drops the price placeholder). `resolveVariantSpecs(variant, release)` (`app/utils/keyboard.ts`) is the one place that works this out (`year`, `price`, `materials`, and `custom`, which drives the _Custom Specs_ badge: a material of its own that differs from the release's, in any order; an own price shows on the card and an own year is not a build spec, so neither counts); the page (once, in its `releases` computed), the drawer, and the copied image use it. `ReleaseForm` always shows the shared specs (fill in only what every variant shares) and offers Top Case only from the keyboard's layouts, with what an empty field takes as its placeholder (_Keyboard: WK_, or _All layouts_ when the keyboard lists none); `VariantForm` always shows its year, price and currency, and materials with the release's values as placeholders (_Release: Aluminum_), saved empty to inherit.
- **Release actions**: a release's Add Variant and Edit / History / Delete beside its name are ghost icon buttons, like the keyset's Add Kit, so they don't read as the keyboard's own actions in the header; an empty release offers Add Variant from its `UEmpty`. One release form, one variant form, and one `SharedConfirmModal` serve the page. _Sort_ (a header button beside _History_, from two releases) opens `KeyboardModalReleaseSortForm`, a drag-handle list of every release, in review included, saved through `POST /api/keyboards/[brand]/[keyboard]/releases/sort` (there is no sort page).
- **Variant drawer**: clicking a variant card opens `KeyboardVariantDrawer` (one `USlideover` for the page, `sm:max-w-2xl`): the full name (`variantTitle`) as its title, the release's description at the top of the body (not in the fixed header, where a long one would crowd the photos), Front / Back / _Side by Side_ photo tabs when both photos exist, `KeyboardVariantBadges`, every spec in a three-column grid `SharedSpecList` (`variantSpecItems(keyboard, release, variant)` in `app/utils/keyboard.ts`, read from the board outwards: design, build, then sale, each resolved through `resolveVariantSpecs`; unset ones show `—`, so every variant lists the same specs), and _Save_ and _Copy Image_ in its footer. `KeyboardVariantCard` is only the copied image: the drawer passes it the same title (`variantTitle`), photos (`variantPhotos(variant, view)`), and specs, laid out in a fixed-width card.

## App layout

- `app/layouts/default.vue`: the sidebar's catalog sections (each module ends with _Submissions_ for signed-in users, with a pending-review badge for staff, see `docs/agents/submissions.md`) and its Leaderboard and Notifications links come from `useSidebarNavigation(collapsed)` (`app/composables/useSidebarNavigation.ts`); the layout adds Feedback and Donate (which open its modals) and builds the search palette groups. The sidebar footer holds only what is used often or carries a badge: Leaderboard (everyone), Notifications (signed-in only, `bell-dot` icon and a `9+`-capped badge counting unread notifications plus unread announcements; it links to the Announcements tab when only announcements are unread), Feedback (kept in sight so reporting a problem never takes a search), and Donate. The page wrapper beside the sidebar is `flex-1 min-w-0` (never `w-full`, which overflows the window by the sidebar's width) and `*:min-h-0`, so the panel (`min-h-svh` by default) shrinks under the announcement banner. `ProfileMenu.vue` holds the rest, in groups: Settings, _Appearance_ (a submenu with the color modes and the palettes as two groups labeled _Theme_ and _Palette_, as on the Appearance settings page, kept open while picking), and _About_ (a submenu: About Keebdex, Changelog); for staff, Recent Changes and, for admins, the _Management_ submenu; then Sign Out (guests: Sign In, Appearance, About). The search palette's Links group also lists Recent Changes (staff), About Keebdex, and Changelog, from the same `RECENT_CHANGES_LINK` and `ABOUT_LINKS` (exported beside `useSidebarNavigation`) as the profile menu; its trigger shows the avatar with the name and role, or only the avatar when `collapsed` (collapsed sidebar, mobile navbar), and only then does the menu header add the role.
