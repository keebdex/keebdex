# Catalog Pages

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

The public catalog pages: the home page, the keyset pages, and the keyset and keyboard detail pages, plus the cards and header actions every detail page shares.

## Detail page conventions

- **Cards**: Variant cards, keyset kit cards, and the sculpt page's colorway cards are one `SharedCatalogCard` (`app/components/shared/CatalogCard.vue`): the image (`aspect` `video` with a `fallback` image, or `square` with an icon placeholder), the name with a formatted `price` (`price-struck` when cancelled), a two-line description, a `badges` slot over the image, Add Photo (for suggesters, emits `suggest` like Edit), and a footer with `footer-start` (_Save_ with its label through `SharedSaveToCollection keep-label`, or a kit's units) on the left and Edit / History / Delete as ghost icon buttons on the right, from `SharedRecordActions` (`editable` for staff: edit in place, History, and Delete only where the page binds `@delete`, which `deletable` can still gate, e.g. a release with variants; `suggestable` alone: Edit suggests; emits `edit`, `suggest`, `history`; `ghost` on cards and release rows, the theme's button style otherwise; `label` names the buttons, e.g. _Edit Release_; the icons are fixed, `edit-01` and `file-remove`, so every module shows the same ones; its tooltips render only in the browser, in `ClientOnly` with the bare buttons as fallback, so card grids don't render a tooltip tree per button on the server), which the card wraps and release headers use directly.
- **Headers**: Page headers (maker, sculpt, brand, keyboard, keyset profile, and keyset pages) use it too (only the sculpt page binds `@delete`), and every other header action is icon-only with a tooltip and an `aria-label` (Sort, Pins, the _Info_ drawer of `SharedProfileDrawer`), except the primary Add button (Add Sculpt, Add Colorway, Add Keyboard, Add Release, Add Keyset) and _Save_, which keep their labels. Every header keeps one order: the labeled primary action (Add, or _Save_ on the keyset page), then Edit / History / Delete, then the page's own tools (Sort Releases, Customize Pins, Add Cover), then the drawers (_Info_). The keyboard page has no `UPageHeader`: its actions sit in its catalog entry, in the same order. List controls are not header actions: the sculpt page's sort select sits in a `UDashboardToolbar`, like other list pages. The edit forms and `SharedRevisionHistory` (no button of its own, opened through its `show()`) sit with the page's other staff modals; colorway cards on the sculpt page (`app/pages/artisan/maker/[maker]/[sculpt].vue`) use the same footer, which wraps the icons to a second row on narrow cards, backed by one colorway form. Pages that delete their records from cards share one `SharedConfirmModal` through `useConfirmDelete(onDeleted)` (`target`, `deleting`, `open(entity, name, url, then?)`, where `then` replaces `onDeleted` for that call, e.g. to leave the sculpt page after deleting the sculpt, `confirm`) instead of a confirm modal per card.

## Home

- **Home page** (`app/pages/index.vue`): a hero whose actions are _Start Collecting_ (_My Collection_ when signed in, to `/collection`, which shows guests its sign-in page) and a `UDashboardSearchButton` labelled _Search Keebdex_ (opens the `KeebSearch` palette), with _Why Choose Keebdex?_ as a link below; on phones the wordmark drops from `2xl` to `xl` (`$device.isMobile`) and the spacing tightens so _Happening Now_ starts on the first screen. Then the sections in `app/components/home/`, each with its own layout: `HomeFreshReleases` (_Happening Now_, the only bordered panel: makers with their count of new colorways, and live keysets with a days-left badge, warning-colored in the last three days), `HomeArtisanGuides` (an open two-column `UPageSection`), `HomeTopContributors` (the guides' layout mirrored from `lg`, hidden while nobody has contributed this month: this month's top three on `LeaderboardPodium`, beside ranks 4–6 as compact `LeaderboardRow`s, the signed-in user's own rank when they are not among them, and _Full Leaderboard_ / _Start Contributing_, a menu of the three submission wizards; the board renders on the server and the user's rank loads in the browser), and `HomeShoutouts` (an open centered section of `ShoutoutCard`s, rating, quote, then author, shared with `/shoutouts`). Every row goes through `HomeMarquee`, which scrolls only when there are more than `max` items (a few repeated items read as duplicates) and otherwise shows them still (`layout`: `grid`, or `center` at the `itemClass` width), keeping cards one width. Its marquee sets `ui.content: 'w-auto'`, since `UMarquee`'s `w-full justify-around` spreads short lists apart, and the panel holding it uses `lg:flex`, since `UPageSection`'s `lg:grid` track stretches to the marquee and drops the padding.

## Keysets

- **Keyset pages**: sidebar order is Profiles (`/keyset`, catalog from `useKeysetProfiles().groupedProfiles`), Group Buys (`/keyset/group-buy?status=ic|live`; legacy `/keyset?status=…` redirects, and any other value falls back to `live`; `GET /api/keysets?status=`: `ic` is the Interest Check status, `live` every Confirmed keyset whose `start_date`–`end_date` holds today, through `liveGroupBuys(query)` in `server/utils/index.ts`, which the home page's _Happening Now_ in `GET /api/statistics` uses too), Colors, Submissions. Never add a static `profile.vue` here (it collides with the `keyset-profile` route of `[profile]/index.vue`). `/keyset/[profile]` sends the route param as `profile_id`, since the profile list may not be loaded during SSR. Profile logos always invert in dark mode (no `invertible_logo` column). `keysets.status` only says whether a set is going ahead (`KEYSET_STATUSES` and `KeysetStatus` in `app/utils/keyset-status.ts`, from the `keyset_status` enum in the generated types): Interest Check (not decided yet), Confirmed (happening, from group buy to delivery; `DEFAULT_KEYSET_STATUS`, also the column default), or Cancelled; the column is a not-null enum (migration `20261028000000_keyset_status_cleanup`). `keysetPhase(keyset)` gives the badge: Live by the same rule (Confirmed and dates hold today), else the status; `keysetPhaseColors` colors Live and Cancelled. Today is the UTC date (`isoToday` in `date.ts`), on the server and in the browser alike. Never write another status or null; catalog-sync sends none and gets the default.
- **Keyset detail page** (`[profile]/[keyset]/index.vue`): the cover (keyset `img`, else first kit) is hidden when missing or broken, with no placeholder; `UPageHeader`'s `#links` (beside the title, except under it beside the cover from `lg` to `xl`, where the column is too narrow for both) hold _Save_ with its label, then Edit and History (`SharedRecordActions`); the reference links sit under the specs as labeled buttons: _Geekhack_ (only when `url` is a geekhack thread; vendor pages are left out, since they go stale once the group buy ends), _Order Graph_, and _Order History_ (dvorcol's charts, opened in the preview modal); the navbar keeps only the title and breadcrumb. Kits and Color Palette are headed by a section-sized `UPageHeader` (`detailSectionHeaderAs` / `detailSectionHeaderUi` in `app/utils/index.ts`: an h2 title, no border or padding, actions beside the title; the color note is its description), with a ghost icon-only Add in `#links` (Add Kit: staff open the kit form, other signed-in users go to the submission wizard; Add Colors: staff only), and fall back to `UEmpty`. Kit cards keep units on the left of the footer and ghost Edit / History / Delete on the right; colors are only added and removed (Remove beside the name in `KeysetColorCard`'s `action` slot), with no per-color history, since color changes are revisions of the keyset. One kit form, one color form, and one `SharedConfirmModal` serve the page; there are no `kit`/`color` sub-pages; one _Specifications_ group (designer, row sculpt, IC date, timeline, status as a badge), headed like Kits, is a three-column grid `SharedSpecList` with icons; kit cards show `price`/`qty` when set; one preview modal serves kits, cover, and order graph/history; opened from a kit, it shows a looping `UCarousel` of the kits that have an image (swipe, arrows, a position counter; the title and description follow the selected kit). The carousel handles arrow keys only while focused, so the page adds left/right `defineShortcuts` while a kit is shown, skipped when focus is already inside the carousel; `start-index` comes from a separate `kitStart`, since changing it re-initializes Embla.

## Keyboards

- **Keyboard detail page** (`app/pages/keyboard/brand/[brand]/[keyboard]/index.vue`), laid out as a catalog entry; the navbar keeps only the title and breadcrumb, and every section after the first opens with a top border and a section-sized `UPageHeader` (`detailSectionHeaderAs` / `detailSectionHeaderUi`). Releases follow `order` (staff set it through Sort, newest first) and only published (`isApproved`) releases and variants show; for the record and the featured photo, every variant is also a `variantRow(variant, release)` (`app/utils/keyboard.ts`: name, release, and year, price, sale, finish, and units resolved through `resolveVariantSpecs`; year and units undefined when unset).
  - **Catalog entry**: two columns from `lg` (photo 3/5, sticky beside the taller record; stacked on phones). The photo is the featured variant (the first variant with a photo until another is picked; eager, `fetchpriority="high"`, `sizes` of its own) with its name, release, year, and price over a gradient, opening the variant drawer; under it a filmstrip of every variant photo (a listbox; picking one features it). Beside it: the brand (logo and link), the name as the page's h1, the catalog ID (`brand_keyboard_slug`, mono) with the _Based on_ link (`derived_from`), the description (`SharedDescription`, which renders one paragraph per line in a single `space-y-2` root, so classes passed to it apply), the actions for signed-in users (Add Release with its label, then `SharedRecordActions`, then Sort), and the record: two hairline `dl` groups, _Design_ (`keyboardSpecItems`: Form Factor, Top Case only for `keyboardTopCaseStylesEnabled`, Mount, Typing Angle) and _Record_ (`keyboardRecordItems(keyboard, releases, rows)`: Produced, the year range of releases and variants; Releases; Variants; Units Produced, the known runs summed, `+` when some are unknown; Sale Formats; Finishes; Last Verified, the newest `verified_at` of the keyboard, a release, or a variant, formatted from its UTC day so SSR and hydration agree), `—` when unset. Materials, price, and units stay with releases and variants (`keyboards` has no material columns).
  - **Production History**: the releases on a rail (`ol` with a left border and a dot per release). The rail column names each release, with its year under the name when set (a 10rem column from `sm`, above the rest on phones; no variant count). Beside it: the description clamped to three lines (the variant drawer shows it in full), its specs as a `SharedSpecList` (`releaseSpecItems`: Top Case only when the release narrows its keyboard's layouts, then materials), with the ghost actions on their right (Add Variant, then `SharedRecordActions`, Delete only once the release has no variants), then its variants as a `UPageGrid` of `SharedCatalogCard`s (two columns from `lg`, three from `xl`, since the rail and year column narrow it; finish as the description, price, a _Custom Specs_ badge, _Save_, ghost Edit / History / Delete; clicking one opens the variant drawer), or _No variants recorded yet_. There is no variant table and no filters.
  - **Lineage**, when the keyboard has an original or derived designs: a `UPageGrid` with the original (`UPageCard` with an icon) and each derived keyboard (`cover_image` from `GET /api/keyboards/[brand]/[keyboard]`, `imageCardContainerClass`).
  - With no published release, `UEmpty` (_Nothing Has Shipped Yet_) replaces the history. `SharedSpecList` (`app/components/shared/SpecList.vue`, also on keyset pages and in the variant drawer): `layout` `divide` by default, a row with subtle separators, or `grid`, even columns, four unless `columns` is 3; both by container width, two columns when narrow; an item's `badge` replaces its text.
- **Spec inheritance**: Specs are set once and inherited downward: the keyboard holds form factor, mount, typing angle, and every layout it supports (`top_case_styles`, for `keyboardTopCaseStylesEnabled` form factors); a release holds year, price and currency, materials, and optionally the subset of layouts it was sold in (`keyboard_releases.top_case_styles`, null for all; `hasTopCaseStyles(keyboard)` says whether the form factor has layouts); a variant leaves each of year, price, currency, and materials empty to take its release's and sets one only where it differs (a price of its own is read in its own currency, else the release's). `resolveVariantSpecs(variant, release)` (`app/utils/keyboard.ts`) is the one place that works this out (`year`, `price`, `materials`, and `custom`, which drives the _Custom Specs_ badge: a material of its own that differs from the release's, in any order; an own price shows on the card and an own year is not a build spec, so neither counts); the page (once, in its `releases` computed), the drawer, and the copied image use it. `ReleaseForm` always shows the shared specs (fill in only what every variant shares; a commission or special drop leaves the rest to each variant) and offers Top Case only from the keyboard's layouts; `VariantForm` always shows its year, price and currency, and materials with the release's values as placeholders (_Release: Aluminum_), saved empty to inherit. Published means `isApproved` (`suggestions.ts`).
- **Release actions**: A release's Add Variant (signed-in users; staff open the variant form, others go to the submission wizard) and Edit / History / Delete beside its name are ghost icon buttons too, like the keyset's Add Kit, so they don't read as the keyboard's own actions in the header; an empty release offers Add Variant from its `UEmpty`. Staff actions are visible buttons backed by one release form, one variant form, and one `SharedConfirmModal`; _Sort_ (a header button beside _History_, from two releases) opens `KeyboardModalReleaseSortForm`, a drag-handle list of every release, in review included, saved through `POST /api/keyboards/[brand]/[keyboard]/releases/sort` (there is no sort page).
- **Variant drawer**: Clicking a variant card opens `KeyboardVariantDrawer` (one `USlideover` for the page, `sm:max-w-2xl`): the full name as its title (brand, keyboard, release, variant), the release's description at the top of the body (not in the fixed header, where a long one would crowd the photos), Front / Back / _Side by Side_ photo tabs when both photos exist, the sale and photo credit badges (`KeyboardVariantBadges`), every spec in a three-column grid `SharedSpecList` (`variantSpecItems(keyboard, release, variant)` in `app/utils/keyboard.ts`, read from the board outwards: design (form factor, the release's layouts, mount, typing angle), build (case, finish, plate, PCB, weight), then sale (year, sale type, price, units), each resolved through `resolveVariantSpecs`; unset ones show `—`, so every variant lists the same specs), and _Save_ and _Copy Image_ in its footer. `KeyboardVariantCard` is only the copied image: the drawer passes it the same title (`variantTitle`), photos (`variantPhotos(variant, view)`), and specs, laid out in a fixed-width card.
