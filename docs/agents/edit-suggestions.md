# Edit Suggestions

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

Signed-in users who cannot edit a page suggest changes to its **published** records (null/`Approved`, not `deleted`): a missing photo, a wrong date, price, or spec, a maker's, profile's, or brand's details, or a keyset's colors. New records still go through the submission wizards; `Pending`/`Rejected` records are edited by their submitter and take no suggestions. Migrations `20261017000000_edit_suggestions` (after the notification migrations) and `20261026000200_catalog_parent_suggestions` (makers, profiles, brands, keyset colors).

- **Forms**: suggestions are made in the record's own atomic form, so new form fields become suggestable without extra work. `SharedSuggestionForm` renders it with `mode="embedded"` (plus KeysetForm's date range) and reports the changed columns (`suggestionDiff`: keys present on the record, plain column values only, protected ones skipped, values normalized: calendar dates to ISO, blanks to null). Forms with fields a suggestion cannot change take a `suggest` prop that hides them (ColorwayForm: order; KeysetForm: profile, review status; ReleaseForm: unique specs per variant; VariantForm: release; MakerForm: verified, Google Doc settings); KeysetForm's `suggest` also shows _Colors_ (`KeysetColorPicker`, the color search shared with `KeysetColorForm`), since staff manage colors on their own page. Profiles use `KeysetModalProfileForm` (also the admin _Edit_ on `/keyset/[profile]`, saved through `POST /api/profiles/[profile]`, update only, 403 when RLS refuses). Uploads go through each form's own `SharedImageUpload`.
- **Registry**: `app/utils/suggestions.ts` (`SUGGESTION_ENTITIES`): per record type (`artisan_colorway`, `artisan_sculpt`, `artisan_maker`, `keyset_kit`, `keyset`, `keyset_profile`, `keyboard_variant`, `keyboard_release`, `keyboard`, `keyboard_brand`) its table, label, name column, default `formProps(record)`, and `protected` columns (keys, parent links, order, Google Doc sync columns) on top of `SYSTEM_FIELDS` (ids, timestamps, `fts`, moderation). `edit_suggestion_protected_fields()` in the migration must list the same columns. Renames move the page like the admin forms do: `slugKeys(name)` builds the record's own slug from a changed name (sculpt `sculpt_id`, keyset and keyboard `slug`), `SharedSuggestionForm` adds it through `withSlugKeys` before diffing (the record's slug when the name is unchanged), and undoing the slug (`isSlugKey`) undoes the name; page keys stay protected (see "Server and Supabase Rules" in AGENTS.md). Display helpers: `suggestionFieldLabel`, `formatSuggestionValue`, `isImageSuggestionField`, `suggestionRecordPath`, `isSuggestable`. Makers, profiles, and brands (`OWNER_ENTITY_TYPES`) are their own key, so their key (`maker_id`, `profile_id`, `slug`) stays protected and a rename only changes `name`; the Edits queue lists them under the owner column. A keyset's colors are a field that is not a column (`isVirtualSuggestionField`, `edit_suggestion_virtual_field()`): records and forms hold them as sorted color ids (`suggestionRecord` maps the keyset page's color rows), a suggestion holds `{ add, remove }` (`colorsChange`, `colorsAfter`, `isColorsChange`), never the whole list, and `SharedSuggestionChange` shows them as swatches (removed red, added green), loading color details by id through `useKeysetColorDetails` (`GET /api/colors?ids=`).
- **Table** `edit_suggestions` (`entity_type`, `entity_id`, `domain`, `scope`, `parent_key`, `changes`, `original`, `applied`, `reason` ≤ 500, `review_status`, `review_note` ≤ 280, `submitted_by`, `verified_*`). The `guard_edit_suggestion` trigger accepts only columns of the record's table that are not protected (`edit_suggestion_field_allowed`), casts the values to the table's row (a wrong type fails), fills `domain`/`scope`/`parent_key`, captures `original`, drops unchanged fields, files inserts as `Pending` under `auth.uid()`, lets only the submitter edit `changes`/`reason` while Pending, lets only staff of `scope` review (once; Reject needs a note), and allows `Approved` only through `apply_edit_suggestion`. One Pending suggestion per user and record. Scope follows each table's RLS: `maker_id` (makers, colorways, sculpts), `profile_keyset_id` (keysets, kits), the keyboard's `brand_slug` (keyboards, releases, variants), a brand's `slug`, and a profile's `profile_id` (nobody is assigned one, so admins and editors without assignments review profiles). For a keyset's `colors` the guard (`parse_colors_change()`) keeps only adds the keyset lacks and removals it has, rejects other shapes, unknown colors, and a color in both lists, and stores the keyset's colors in `original.colors`. Deleting a record deletes its suggestions. RLS: submitters read theirs and update/delete them while Pending; staff read, update, and delete their scope.
- **Apply**: `apply_edit_suggestion(p_id, p_changes)` (security invoker, so the record's RLS applies) writes the changes staff approved to the record and approves the suggestion with `applied` in one transaction. A keyset's colors are applied as a change, not a list: colors to add it still lacks are added, colors to remove it still has are removed, and every other color stays (also colors added since). For colorways and sculpts it adds applied Google Doc–managed fields to `overridden_fields`, like `ColorwayForm`/`SculptForm`; those fields are `colorwayGdocManagedFields` / `sculptGdocManagedFields` (`app/utils/schemas/artisan.ts`), and the migration repeats them, so change both together.
- **API** (`server/api/suggestions/`, helpers in `server/utils/edit-suggestions.ts`, which reads the table through the untyped `suggestionsTable`; `parseSuggestionChanges` checks keys against `TABLE_FIELDS` and the protected columns, and database errors map through `suggestionError`, 409 for a duplicate Pending one):
  - `GET /?domain=&status=&page=&size=` → `{ data, count }`, each row with `record` (current values), `entity_name`, `parent_name`, and `names` (`owner`: maker, profile, or brand; `page`; `release`; `item`: colorway, kit, or variant), whose extra joins (`NAME_JOINS`) are dropped from `record`.
  - `POST /` `{ entity_type, entity_id, changes, reason? }`; `GET /pending?entity_type=&entity_id=` (the caller's Pending one); `POST /:id` (staff `{ action: 'approve', changes? }` or `{ action: 'reject', note }`, submitter `{ changes?, reason? }`); `DELETE /:id`.
  - Staff only (`requireRevisionStaff`), for the review modal: `GET /:id/changes-since` → `{ data: { [field]: revisions } }`, per field the revisions walking back from the newest to the one made from the `original` value (a submitter's edit captures `original` again), each `changes` narrowed to that field; `GET /:id/overlapping` → `{ data }`, the other Pending suggestions for the record that share a field, shaped like queue rows plus `overlap` and `submitter_name` / `submitter_avatar` (`getActorNames`, the `revision_actors()` lookup also behind `withRevisionActors`).
- **Client**: on the maker, sculpt, profile, keyset, brand, and keyboard pages, signed-in users who cannot edit see the same _Edit_ buttons as editors (headers, releases, card footers), plus _Add Photo_ / _Add Cover_ on records without an image; `useSuggestEdit(editable)` opens one `SharedSuggestEditModal` (default `UModal`, title _Edit <Record>_): the footer counts the changes, and _Review Changes_ shows each one (current and new value, Undo through `SharedSuggestionForm`'s exposed `reset(key)`) with the optional reason before _Submit for Review_; it reopens the user's Pending suggestion to update or withdraw it.
- **Edits queue**: review pages have New / Edits toolbar tabs (`useSubmissionViews`, `?view=edits`, each with a pending-review badge for staff); Edits is `SharedSuggestionQueue` (status filter, pagination, Review/View, Delete or Withdraw). Its name columns follow the module from `names`, named like the New tab's: artisan Name (the colorway title, or the sculpt) and Maker; keyset Keyset and Kit; keyboard Brand, Keyboard (with the release), and Variant.
- **Review modal** (`SharedSuggestionReviewModal`): current vs suggested per field (`SharedSuggestionChange`, shared with the Edit modal's review step; its default slot holds the extras below) with a checkbox each (a keyset's colors as two rows, _Colors to Add_ and _Colors to Remove_, each with its own checkbox, and a warning when a suggestion removes at least half of the keyset's colors); _Adjust Values_ opens the record's form with the selected changes and approving applies what it holds; Reject offers `SUGGESTION_REJECT_NOTES`. For reviewers it also loads, once per suggestion: `changes-since`, turning a field's _Changed Since_ badge into a `Changed Since · N` toggle that lists those revisions (`SharedSuggestionChangesSince`: authors, before → after, time, _Open in History_ in a new tab); and `overlapping`, adding _Also suggested by_ lines (`SharedSuggestionAlsoSuggested`: submitter, value, time) whose _Review_ switches the modal to that suggestion (`@open`, handled by the queue). Several suggestions for one field are reviewed one at a time on purpose; a merged review was considered and left out while they are rare.
- **Notifications**: `suggestion_status` (approved / rejected with the note, grouped per parent, status, and note) with preference keys `suggestion_approved` and `suggestion_rejected` (Edit Suggestions group).
