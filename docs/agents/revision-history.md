# Revision History

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

Every insert, update, and delete on the catalogue tables (makers, sculpts, colorways, profiles, keysets, kits, brands, keyboards, releases, variants) and every change to a keyset's colors is kept in `record_revisions` (migration `20261021000000_record_revisions`, after the edit suggestion migration; makers, profiles, brands, and colors from `20261026000100_catalog_parent_revisions`), like a wiki history. It is append-only, staff-only, and doubles as the audit of catalogue content: Pending/Rejected rows, approvals, and rejections are recorded too.

- **Trigger** `record_revision(entity_type)` (after each row change, security definer) writes `snapshot` (the row after the change, or before a delete, without `fts`), `changes` (`{ field: [before, after] }` for updates), `domain`, `scope` (as in RLS: `maker_id`, `profile_keyset_id`, the keyboard's `brand_slug`; a profile's own `profile_id`, which nobody is assigned, so only admins and editors without assignments read it), `parent_key` (the page's key, so one filter returns a page and its children; makers, profiles, and brands are their own key: `maker_id`, `profile_id`, `slug`), `label` (name at the time), `actor` (`auth.uid()`), and `source` (`revision_source()`). Updates that change only `record_revision_ignored_fields()` (`fts`, `updated_at`, `order`, `source_document_id`, `overridden_fields`, and a maker's `contributors`, which the Google Doc sync rewrites) write nothing.
- **Keyset colors**: statement triggers on `keyset_colors` (`record_keyset_colors_revision()`, one per event because of transition tables) write one revision of the keyset per statement with `changes = { colors: [ids before, ids after] }`, sorted ascending and deduplicated; a color the keyset already had counts as kept, and the on update cascade of a renamed keyset writes nothing. A keyset's snapshot holds no colors, so _Restore_ leaves them alone. `GET /api/revisions/:id` returns a keyset's `current.colors` the same way (`suggestionRecord`, with the join from `VIRTUAL_FIELD_JOINS`), and `SharedSuggestionChange` shows them as swatches (removed ones red, added ones green), loading the colors by id through `useKeysetColorDetails`.
- **Sources**, in order: `suggestion` (`keebdex.applying_suggestion`, set by `apply_edit_suggestion()` before it updates the record; `suggestion_id`), `revert` (`keebdex.reverting_revision`; `reverts_revision`), the `x-keebdex-source` header (`gdoc`, `scraper`, `vendor`, `image-sync`, `maintenance`, plus `run_id` from `x-keebdex-run`), trusted only when the JWT role is `service_role`, then `app` with a user, else `sql`. catalog-sync sends the headers through `createSupabase(source)`.
- **Renames**: updates that only follow a renamed parent through an on update cascade (every changed field links to a parent whose old key no longer exists: a sculpt's colorways, a keyset's kits, a keyboard's releases and variants, `is_revision_of`, `derived_from`) write nothing, so a rename is one revision of the renamed page; moving a record to another existing parent is still recorded. When a page key changes, the trigger re-points the revisions and edit suggestions under the old `parent_key` to the new key and scope (`guard_edit_suggestion` allows that only under `keebdex.rekeying`). Renaming a keyset, a maker (`maker_id`), or a brand (`slug`) also replaces its key in `users.assignments` so its staff keep access; under the same flag `guard_user_role` lets non-admin editors through and `notify_account_role_changed` sends nothing.
- **Not built yet**: a renamed sculpt, keyset, or keyboard answers its old address with a 404 (no redirects), and nothing stops renaming a published page, unlike makers, profiles, and brands, whose key is fixed once published (`guard_owner_key()`). If either is wanted later: a `catalog_redirects (domain, old_key, new_key)` table written by the rename (chains collapsed, a key reused by a new page clears its row) and read only when a detail page 404s, so normal page views cost nothing; and the same guard on page keys, which also needs catalog-sync's `source_slug` matching kept in mind.
- **Access**: RLS select `can_manage(scope)`; insert, update, delete, and truncate are revoked from `anon`/`authenticated`, so only the trigger writes and only the service role deletes. `revision_actors(ids)` (security definer, `can_manage_any()`, 100 ids) returns names and provider avatars, since staff other than admins cannot read `users`; both it and the leaderboard read them from the internal `user_display(id)` (`20261027000000_leaderboard`), so a user is named the same everywhere.
- **Revert** `revert_revision(p_id, p_mode)` (security invoker, so the record's RLS applies): `undo` writes back the `before` values of an update and fails with SQLSTATE `RV409` (fields in the detail) when any of them changed since (a keyset's colors only when it no longer has exactly the colors after, and then only the colors that differ are removed or added); `restore` writes every snapshot column that differs from the record now. Both skip `edit_suggestion_protected_fields()`, refuse deleted records, record a `revert` revision, and add reverted sync-managed fields of `gdoc`/`scraper` colorways and sculpts to `overridden_fields`.
- **API** (`server/api/revisions/`, helpers in `server/utils/revisions.ts`, untyped `revisionsTable`; staff only through `canManageAnyAssignment`):
  - `GET /?domain=&parent_key=&entity_type=&entity_id=&run_id=&source=&hide_syncs=&before=&groups=` → `{ data, hasMore }`, newest first, paged by groups of consecutive revisions (`revisionGroupKey`): by page without `parent_key` (Recent Changes), one revision per group with it (History). A page holds `groups` (default 20, at most 50) complete groups, read 200 rows at a time (at most 10 reads); `before` is the last revision id returned. `parent_key` needs `domain`; `entity_type` + `entity_id` narrow to one record, `run_id` to one sync run; `source` is a `REVISION_SOURCE_GROUPS` key (`editors`, `suggestions`, `syncs`) and `hide_syncs=1` drops syncs. Rows leave out snapshots and changes (`REVISION_LIST_COLUMNS`) and carry `record_name` / `variant_name` (from the snapshot), `actor_name`, `actor_avatar`, and `suggested_by` (with avatar); without `parent_key` also `parent_name` (`withParentNames`: the page name after its maker, profile, or brand, as the suggestion queue shows it, through `PARENT_LOOKUPS` / `parentName` in `server/utils/edit-suggestions.ts`).
  - `GET /:id` adds `changes`, `snapshot`, `before` (the snapshot with the changed fields set back), and `current` (the record now, or null).
  - `POST /:id/revert` `{ mode: 'undo' | 'restore' }` → 409 with `data.fields`, 403, or 404.
- **Lists**: History and Recent Changes list revisions the same way: `SharedRevisionDays` puts entries under a heading per day (_Changes today_, _Changes yesterday_, _Changes on <date>_, from `groupRevisionsByDay`), and each entry is a `SharedRevisionCard` (a button: an icon avatar named by its tooltip, the title, authors, an optional verb, time, an optional badge, and a primary outline with an edge bar when `selected`). Authors read like a commit's (`SharedRevisionAuthors`, from `revisionAuthorsOf` / `revisionAuthorList`): stacked avatars, then up to two names (`A and B`, `A, B and 2 others`). An applied suggestion credits its submitter and the approving moderator; sync jobs are named like bot accounts (_Google Docs_, _Maker Sites_, _Vendor Sites_, _Image Sync_, _Maintenance_) with a `bot` badge, and the SQL editor is _Database_ without one. `revisionVerb` gives the action after them (`edited`, `reverted`). Helpers (sources, authors, grouping, diffs, revertable fields, `revisionPagePath`, `groupRecentChanges`) live in `app/utils/revisions.ts`.
- **History** (`SharedRevisionHistory`): the `USlideover` of the maker, sculpt, profile, keyset, brand, and keyboard pages (`editable` only; loads when opened), opened through its exposed `show()` from the page header's History button (`SharedRecordActions`); it renders no button of its own. A maker's, profile's, or brand's history holds only its own revisions; the pages below keep theirs. `SharedRevisionList` shows one row per revision, sync changes included: the record's kind as an icon avatar named by its tooltip (`revisionEntityIcon`, `revisionEntityLabel`; the sidebar's icons where it has one: the module icons for sculpts, keysets, and keyboards, and those of Makers, Brands, and Profiles), its own name (`revisionRecordName`; the page's own revisions use its label), then authors, action, and time, in a `SharedRevisionCard`; clicking a card opens the revision in the slideover as Recent Changes shows it (`SharedRevisionDetail`), with a back arrow (_All Changes_) before the _History_ title to go back.clicking a row opens it. It loads 20 revisions at a time (_Load Older_). It has no footer: a _Recent Changes_ icon button sits beside the close button (the `actions` slot). The exposed `show({ record, revisionId })` narrows it to one record (a badge with _Show All Changes_), used by the _History_ buttons on colorway cards, kit cards, release headers, and variant cards. `?history=1` opens it on load, `&rev=<id>` opens that revision, and closing drops both from the URL.
- **Revision detail** (`SharedRevisionDetail`, `revisionId`): one revision as History and Recent Changes both show it, in a panel or slideover body: the record as a heading with authors, verb, and time (to the minute), _Undo_ (updates only; disabled, with an _Edited Again_ alert naming the fields, when they changed again) and _Restore Revision_, both behind `SharedConfirmModal`, which warns when fields will stop syncing from the maker's Google Doc or website; then its default slot (Recent Changes puts the entry's chips there), a band with how many fields changed on the left and _View Mode_ (Side by Side / Unified, kept for the session in `useState('revision-diff-layout')`) on the right, and the diff. It emits `loaded` (the revision) and `reverted` (the fields the revert wrote); success uses `successToast('update')`, History's `@reverted` refreshes the page and Recent Changes reloads the list. Its logic is `useRevisionDetail({ onReverted })` (`app/composables/useRevisionDetail.ts`): loading a revision (`selectRevision(id)`), what it changed (`changeDiffs`, against the record before it; there is no comparison with the record now), the fields Undo and Restore would write, conflicts, and the confirmation and revert (`confirm(mode)`, `revert()`); `revisionFieldList(keys)` names fields in a sentence.
- **Diffs** (`SharedRevisionDiff`): a card per field with its label and an _Added_ / _Modified_ / _Removed_ badge (from which side is empty), and `layout` `split` (before and after side by side, tinted red and green) or `unified` (a `−` row and a `+` row, empty sides left out); `highlight` adds _Changed Since_. Values render through `SharedSuggestionValue` (shared with `SharedSuggestionChange`): images, a keyset's color swatches, or formatted text, struck through in red or highlighted in green by `tone`.
- **Images**: diffs (`SharedSuggestionChange`) and the Changed Since list render images through `SharedDiffImage` (`compact` for thumbnails), which shows _Image Unavailable_ when the file fails to load: an older value can point at an image `prune-images` deleted, or at a dead external URL. Revisions do not keep pruned images alive; when Undo, Restore, or an approved suggestion makes a record use one again, catalog-sync's daily `restore-images` re-uploads it from the R2 backup under the same id. So the image-sync revision (external URL → Cloudflare URL) is kept on purpose, and revisions need no retention policy until the R2 trash is enabled.
- **Recent Changes** (`/recent-changes`, `ssr: false`, staff only through `isModerator` and `SharedRedirectPage`; sidebar footer link after Notifications, so also in the search palette's Links group): every revision of the caller's scope, as a list and a detail side by side (two `UDashboardPanel`s, the list resizable). The list (`SharedRecentChangesList`) uses the same cards as History (`SharedRevisionDays`, `SharedRevisionCard`); an entry is a run of consecutive changes to a page (`groupRecentChanges`, the API's groups), a card with the module as an icon avatar named by its tooltip (`KEEB_MODULE_ICONS`, as in the sidebar; History names record kinds the same way), the page name, authors and time, and how many changes. Selecting it opens its newest revision in `SharedRecentChangesDetail`: a breadcrumb (module, page link) and an _Open History_ button in its navbar, then `SharedRevisionDetail` with the entry's other revisions as chips in its slot (newest marked _Latest_). On phones the detail replaces the list, with a back button. It loads 20 groups at a time (_Load Older_). Toolbar: module tabs (`domain`) and a _Changed by_ select in the list's navbar (Everyone, Without Syncs, Editors, Suggestions, Syncs; `source`); both and the selected revision (`rev`, which also works for a revision not in the loaded list) are in the URL.
