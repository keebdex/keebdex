# Discovered Keysets

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

The crawler (`magpie` in keebdex/aviary) reads geekhack Interest Check and Group Buy threads into the `ingest` schema (migration `20261119000000_ingest_schema` in `supabase/`): `ingest.threads` (one row per thread, with the first post's `images`) and `ingest.candidates` (what an extractor read, `payload` shaped like the keyset submission body `{ keyset, kits }`, `confidence` per field, `match_key` = the `profile_keyset_id` of a keyset Keebdex already has, `state` `new | promoted | dismissed | superseded`). Staff review the keyset candidates in the **Discovered** tab of the keyset submissions page. "Discovered" covers every crawled source (vendor sites later), so don't call it "Forum Review", and keep it a tab: a static page under `/keyset/` would shadow a profile slug.

- **Access**: `ingest` is not in the generated `Database` type; client and server reach it through untyped handles (`useIngest` in `useDiscoveredQueue`, `candidatesTable` in `server/utils/ingest.ts`). RLS returns candidates to staff only: all of them for `can_manage_all()`, the ones matched to their pages for assigned staff (`ingest.candidate_scope`). `authenticated` may update only `state`, `match_key`, `promoted_kind`, `promoted_id`, `review_note`; `guard_candidate()` allows only `new → promoted | dismissed` and `dismissed → new`, stamps `reviewed_by`/`reviewed_at`, and `candidates_one_new_idx` keeps one `new` candidate per thread and module. The schema must be listed in the Supabase API's exposed schemas.
- **Tab**: `useSubmissionViews` adds _Discovered_ (`?view=discovered`, `solar:radar-line-duotone`) on `/keyset/submissions` only, for moderators (`isModerator`), with the `discovered` count of `GET /api/submissions/pending-counts` as its badge (also part of the sidebar's Submissions badge). `app/pages/keyset/submissions/index.vue` renders `IngestDiscoveredQueue` for it.
- **Queue** (`IngestDiscoveredQueue`, `useDiscoveredQueue`, `useAsyncData` key `discovered-keysets`): state filter (`CANDIDATE_STATE_OPTIONS`), search on the keyset name (`payload->keyset->>name`), pagination, row actions (`IngestCandidateRowActions`: Review opens the approve wizard; Dismiss is a split button that dismisses at once, with _Already on Keebdex_ for a matched candidate and no reason otherwise, and its menu offers every `DISMISS_REASONS` entry or _No reason_; Restore is the undo). Thread images load with `referrerpolicy="no-referrer"`, since several image hosts refuse hotlinks with a referrer (the image provider leaves external URLs unchanged, so the browser fetches them from the host; geekhack attachments load either way). Opening a matched keyset loads it through `GET /api/keysets/:profile/:keyset?all_kits=1` as `current` (null when it cannot be read; the approve modal then shows an error instead of the wizard), and drops kit names that only repeat their category's (`withoutCategoryNames`: Keebdex keeps `name` null unless a kit has its own, e.g. "TKL Base"). Every action reloads the rows and the pending counts.
- **Approve wizard** (`IngestApproveWizard`, `useIngestApproveWizard`): a candidate without `match_key` goes Profile → Keyset → Kits → Review; a matched one Keyset → Kits → Review, its form starting from Keebdex's values with the thread's in the empty fields. `KeysetForm` / `KeysetKitForm` run `embedded`, with their `#image` slot replaced by `IngestImagePicker` (the thread's images, plus Keebdex's current one) and `hide-review-status`. Listed kits are keyed by row `id`: a thread kit updates the one listed kit of its category when there is exactly one, otherwise staff pick it (or _Add as a new kit_); cards of one category must differ by name. A matched keyset may end with no kit (`useRepeatableItems({ min: 0 })`). Its update never changes `profile_id`, and `slug` only with the name. Review (`IngestInsertPreview`) lists every column approving writes, and the payload sends blanks as null exactly as shown.
- **API** (`server/api/ingest/candidates/`, staff only, 404 when RLS hides the candidate, 409 when it was already reviewed):
  - `POST /:id` `{ action: 'dismiss', note? }` (fixed reasons from `DISMISS_REASONS`) or `{ action: 'restore' }`; restore is refused (409) while a newer `new` candidate of the same thread waits.
  - `POST /:id/approve` `{ keyset, kits }`, validated with `createKeysetSchema` (partial for a matched keyset) plus `isoDateSchema` for the dates, and `keysetKitSchema` (400 otherwise; the dates stay out of `createKeysetSchema` because the forms hold them as `CalendarDate`). Assigned staff without `canManageAll` cannot rename a matched keyset (403), since its new page key falls outside their assignment; the wizard locks the name for them (`KeysetForm`'s `lock-name`). With no `match_key` it inserts the keyset (slug from `urlSlugify(name)`, `canManageAssignment` on the new page key) and its kits `Approved`, verified by the caller, with no submitter; with `match_key` (`canManageAssignment` on it) it updates that keyset with the sent columns, updates kits that carry an `id` (scoped to the keyset), and inserts the others `Approved`. Then it marks the candidate `promoted` (`promoted_kind: 'keyset'`, `promoted_id`). A new keyset is deleted again, with its kits, when a later step fails. Thread image URLs are stored as they are; `pelican` copies them to Cloudflare Images.
- **Not yet**: keyboard candidates (the tab is keyset-only) and ignoring threads (`ingest.threads.ignored_at`).
