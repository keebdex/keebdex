# Notifications

Feature reference for Keebdex agents; project-wide rules live in [AGENTS.md](../../AGENTS.md).

Users are notified when staff review or delete their submissions, review their edit suggestions, resolve their feedback, or change their role; the moderator who rejected a submission hears when it is resubmitted. Staff are not notified of new submissions or suggestions; they see pending-review badges instead (see `docs/agents/submissions.md`). Site-wide announcements are separate (see `docs/agents/announcements.md`).

- **Creation**: only Postgres triggers create notifications, through `push_notification(user, type, actor, entity_type, entity_id, data, preference, group_key)` (security definer, not callable by clients). It skips the actor's own actions and preferences the recipient turned off, and merges a notification into the recipient's unread one with the same `group_key` from the last 15 minutes (`data.count`, moved to the top). `notifications` RLS: users read, delete, and update `read_at` on their own rows; no insert. RPCs: `unread_count()`, `mark_all_notifications_read()`. Migrations (idempotent, run in order in the SQL editor): `20261010000000_notifications` (table, preferences, `push_notification`, account trigger), `20261010000100_submission_notifications`, `20261010000200_feedback_notifications`.
- **Submissions**: `keyset_kits`, `keyboard_variants`, and `artisan_colorways` have `review_note` (≤ 280). `guard_submission_review` lets only staff approve/reject or write the note and requires a note to reject; `submission_details()` builds the shared `data` (`domain`, `entity`, `parent_key`, `parent_name`, `submission_name`). Triggers send `submission_status` (grouped by parent, status, and note), `submission_resubmitted` to the moderator who rejected the row (`OLD.verified_by`) on the submitter's `Rejected → Pending` edit, and `submission_deleted` when someone other than the submitter deletes a Pending/Rejected row. Delete endpoints accept an optional staff `{ note }` (`deletionNoteSchema`), saved to `review_note` before deleting so the trigger can send it. Parents never notify. Reject posts `{ id, action: 'reject', note }`; `getModerationOverride` validates it with `reviewNoteSchema`.
- **Account**: changing a user's `role` or `assignments` (by someone else) sends `account_role_changed` with the added and removed assignments. It has no preference key, so it is always delivered.
- **Feedback**: the `attribute_feedback` trigger sets `feedbacks.submitted_by` from `auth.uid()`, so signed-in authors only write a message and admins read their name and email from `users`; guests type a name and an optional email. `POST /api/admin/feedbacks/[id]` takes `{ resolved, note? }` (`resolutionNoteSchema`); resolving sends `feedback_resolved` (`data`: `message` excerpt, `note`) to signed-in authors. RLS: anyone inserts unresolved feedback attributed to themselves; only admins read and update.
- **Notes**: `SharedNoteModal` collects staff notes (counter at 280; required unless `optional`). Reject requires one and offers quick replies (`presets`, from `rejectNotePresets(domain)` in `app/utils/review-notes.ts`: domain-specific replies, then common ones), toggled in and out of the note (picked ones are solid; one item stays a plain sentence, two or more, typed lines included, become a `• ` list, one per line, which notifications keep with `whitespace-pre-line`; a reply that would pass 280 characters is disabled), which stays editable; Resolve takes an optional comment (reads Resolve with Comment once there is text) with quick replies from `RESOLVE_FEEDBACK_NOTES` (same file); deleting someone else's submission takes an optional reason.
- **API** (`server/api/notifications/`): `GET /` (`before`, `unread`, `limit` ≤ 50) → `{ data, hasMore, unread }`, `GET /unread-count`, `PATCH /:id` `{ read }`, `DELETE /:id`, `POST /read-all`, `GET` / `PATCH /preferences`.
- **Client**: `app/utils/notifications.ts` is the registry (`renderNotification`: title, description, `quote`, `note`, icon, color, link). `useNotifications()` shares state and optimistic actions with rollback; All and Unread page from the server separately (`load(filter)`, `loadOlder(filter)`, `unread=1` for Unread, each with its own `created_at` cursor in `cursors`) into one list, and `visibleFor(filter)` shows a filter only down to the oldest notification it has paged to; `plugins/notifications.client.ts` subscribes to realtime INSERT/UPDATE for the user, toasts inserts (grouped updates only refresh the row), refreshes on tab focus, and resets on sign-out. `/notifications` has two tabs, Notifications and Announcements (each with its unread badge), and an Unread / All filter (`UTabs`) for the open tab, Unread by default (`?tab=announcements&filter=all`; the old `?filter=announcements` still opens Announcements), plus day groups, Load older (per filter: _Load older unread notifications_ under Unread), Mark all as read next to the first day group (when the open tab has unread items), an empty-state Show All action under Unread, and rows built on `NotificationRow` (shared with announcements: icon, title with unread dot and time, description, extra content, a link button below, hover actions): a View button below goes to the target and marks read; hover reveals read/unread and delete; rows themselves don't navigate.
- **Preferences**: `notification_preferences (user_id, preference, enabled)`; a missing row means on. Keys and groups live in `app/utils/notification-preferences.ts` and drive `/account/settings/notifications` (groups in order Announcements, Submissions, Edit Suggestions, Feedback; a switch per key, saved immediately, with the item's `icon`/`color` (matching its notification) in multi-item groups; `staffOnly` items such as Submissions → Resubmitted show only to staff, and a group with no visible items is hidden). `announcement_toasts` (Announcements group) is not a notification type: `GET /api/announcements` reads it to turn announcement toasts off.
- **Adding a type**: add a renderer, a preference key (unless it must always be delivered, like `account_role_changed`), and a trigger calling `push_notification()` with that key.
