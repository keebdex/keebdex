# Keebdex Agent Instructions

This is the canonical instruction file for every AI coding agent working in this repository (Claude Code, OpenAI Codex, Cursor, GitHub Copilot, and others). Keep it as the single source of truth: `CLAUDE.md` imports it, and `.github/copilot-instructions.md` points here. Update this file instead of creating agent-specific copies.

## Project Overview

Keebdex is a Nuxt 4 application for keyboard collectors. It uses Vue 3, TypeScript, Nuxt UI, Tailwind CSS, Pinia, Nuxt Nitro/H3, and Supabase PostgreSQL.

Use Bun for local commands. The repository contains a `bun.lock` file.

## Quick Start for Agents

1. Read this file, then the task plan in `.ai/plan/` if one applies.
2. Locate the closest existing pattern (same domain, same kind of file) and follow it before inventing a new one.
3. Keep the diff focused. Do not refactor unrelated code or touch generated files.
4. Verify with the narrowest relevant check first (see "Formatting and Validation"), and report only the checks that actually ran.
5. Do not commit, branch, or open a PR unless the user asks (see "Git and Documentation").

## Important Commands

- `bun run dev`: start the Nuxt development server. The `predev` hook generates database field metadata first.
- `bun run build`: build for production. The `prebuild` hook generates database field metadata first.
- `bun run generate`: generate the static site; this also runs the metadata generation hook.
- `bun run generate:table-fields`: regenerate `server/utils/table-fields.generated.ts` from the database types.
- `bunx eslint .`: run ESLint. Use `bunx eslint . --fix` for automatic fixes; there is currently no `lint` script in `package.json`.
- `bun run preview`: preview a production build.

There is no test script or test suite currently defined in `package.json`. Do not claim tests passed unless a relevant check was actually run.

In save mode it always renders for signed-in users and ends with a New Collection item that opens `CollectionModalCollectionForm` with the item's category preset and `lock-category`; in move mode it hides when no other collection of the category exists. It has two roots (menu and modal), so it sets `inheritAttrs: false` and binds `$attrs` to the menu.

The endpoint pages collections with at least one listed (`exchange`) item, newest first (`size` default 20, capped at 50; an inner join on the items keeps empty collections out of pages and the total; `intent=want|sell` narrows to one kind), and returns `{ data, total }` with each collection's listed `items` (colorway with sculpt and maker names). Item listing fields (Still Looking / Available, price, priority) and the found/sold overlay exist only for `want`/`sell` collections. Collection pages show Share, Manual Sort, Edit, Delete, and item actions only to the owner (`isOwner` from `useCollection`), since shared collections are public. The form prefills the Discord username from `userStore.social.discord` (also when the profile loads after the form opens). `POST /api/users/:id/collections` and `/collections/:collection` are session-owner-only; inserts take `uid` from the session and updates return 404 when RLS changed no row. ## Vue and Nuxt Conventions

- Follow the existing Vue 3 Composition API style with `<script setup>`.
- Keep Vue single-file component blocks in this order: `<template>`, then `<script setup>` (or `<script>` when required), then `<style>`.
- Use TypeScript for new application code unless the surrounding file is intentionally JavaScript.
- Keep components in PascalCase. Keep variables and functions in camelCase. Use snake_case for database identifiers.
- Keep domain-specific components in their existing domain folders; put genuinely reusable components in `app/components/shared/`.
- Prefer existing Nuxt UI components and the established slots/configuration over custom replacements.
- Use `NuxtImg` for optimized images where appropriate. The default image provider (`app/providers/cloudflare-images.ts`, registered as `cloudflare`, which overrides @nuxt/image's built-in Image Resizing provider of that name; it must stay the default because presets cannot set a provider) turns stored Cloudflare Images URLs (`…/<id>/public`, ids may contain slashes) into flexible variants (`…/<id>/w=<n>,fit=scale-down`, width rounded up to a fixed ladder) whenever `sizes` applies, and returns every other source unchanged. Give images a preset from `nuxt.config.ts` (`square` for artisan colorway and sculpt grids, `cover` for keyset and keyboard grids and the related keyboards drawer, `thumb` for submission thumbnails) or a `sizes` of their own for other layouts (the keyset detail cover, the marquee); preset sizes are measured shares of the viewport, so re-measure them when a grid's columns change. Grid and thumbnail images also take `loading="lazy"` and `decoding="async"`; the above-the-fold keyset detail cover loads eagerly with `fetchpriority="high"` instead. Leave images captured by `SharedSnapshot` or opened in previews on the stored URL. Brand, maker, and profile logos (`${imgUrl}/logo/<slug>.png`) are fixed 500×500 files on R2, not Cloudflare Images, so they never get a preset.
- Cards with an image above the title (`UPageCard` with `reverse`) use `imageCardContainerClass` (`app/utils/index.ts`) as their `container`, which pins the grid column to the card so footer actions cannot widen it; footers wrap (`pageCard.slots.footer` in `app/app.config.ts`), and a custom action row inside the footer needs its own `flex-wrap`. Artisan grids use `artisanGridClass`.
- Empty states use `UEmpty` (naked by default; Carbon overrides it to `subtle`) with an `icon`, a Title Case `title`, a one-sentence `description`, and `actions` for a next step. Keep `UPageSection` / `UPageCTA` for content sections and calls to action (e.g. `SharedProtectedPage`). In-page view switchers in the toolbar `UNavigationMenu` take icons or not per page, whichever reads better there (e.g. the `/notifications` tabs have icons).
- Follow the existing mobile-first Tailwind styling and the design tokens in `app/app.config.ts` and `app/assets/main.css`.
- Use the centralized icon names configured in `app/app.config.ts` rather than introducing arbitrary icon sets.
- Buttons with an icon hide their label below `md` (`app/app.config.ts`). Pass `ui: { label: 'block' }` (or use the default slot) when the text must stay visible on phones, e.g. empty-state actions.
- Copied/downloaded images must not depend on the screen size. Render what is captured inside `SharedSnapshot` (off screen, client-only, rendered only while capturing, optional fixed `width`, waits for images) and call its exposed `capture()`; content with its own fixed size (the 380px trading card in `ArtisanColorwayCard`) may be captured in place. Use the helpers in `app/utils/screenshot.ts`: `captureScreenshot`, `copyBlob` (pass the capture promise so the clipboard write stays in the click gesture, as Safari requires), `downloadBlob`, `shareBlob`/`canShareFiles`. Current users: the wishlist sheet, the sculpt page colorway card (18rem), and `KeyboardVariantCard` (48rem, renders itself with `snapshot`; `SharedDescriptionList :responsive="false"` keeps the desktop layout).
- Signed-out gates use `SharedProtectedPage` (`icon`, `title`, `description`, optional `features`, `navTitle` for the mobile navbar, and `signInLabel`).
- Invert dark logos with the Tailwind `dark:invert` class (e.g. `ui.image: invertible && 'dark:invert'`), never with a `useColorMode().value === 'dark'` check: with a `system` preference SSR cannot know the mode and the class mismatch is not patched on hydration.

## Theme Preset System

- Presets are stored in `app/utils/theme-presets/` and registered in `index.ts`. Each preset exports a `ThemePreset` object defining `id`, `label`, `icon`, `font`, `ui` (Nuxt UI config), and `css` (semantic token overrides).
- The CSS shape supports `root`, `html`, `body`, and `headings` blocks plus `light`/`dark` mode variants. The `presetToCss()` function serializes these into inline style blocks injected at runtime via the theme plugin.
- `useAppTheme()` composable persists the selected theme to a cookie (`app-theme`) and provides `themeId`, `preset`, `presets`, and `setTheme(id)` for reactive switching.
- The theme plugin (`app/plugins/theme.ts`) watches the preset and applies its UI overrides to `appConfig`, merging font/color/variant defaults while preserving the app's base icon pack and component config. Font variables from the preset are applied as CSS custom properties and referenced by Nuxt Fonts configuration.
- `useAppTheme()` resolves ids through `findPreset()`, so an unknown or removed id falls back to `DEFAULT_THEME_ID`. Apply themes only through `setTheme(id)`; both the Appearance settings tab and the profile menu (`ProfileMenu.vue`) switch themes with `setTheme` and color mode with `useColorMode().preference` (`system | light | dark`), so new theme or color-mode behavior should hook into those two values rather than into each component.
- Theme switching does not reload the page; the selected theme is persisted in the `app-theme` cookie. Color mode uses `useColorMode().preference` and is persisted in a cookie through `colorMode.storage`.
- Signed-in appearance preferences are stored in `public.users.appearance` as a JSON object with optional `theme` and `colorMode` keys. `app.vue` invokes `useSyncAppearance()` once; it applies server values after `GET /api/users/:id`, seeds the server from local preferences when empty, and refreshes on tab visibility. Changes are saved by `userStore.saveAppearance()` through `PATCH /api/users/:id/appearance` with a 500 ms debounce. The endpoint validates both fields and merges into the existing JSON object. Store `system` as the preference, not a resolved light/dark value.
- Each preset maps `error`, `success`, and `info` to palettes in its own tone rather than Tailwind's bright defaults; only Aurora uses Tailwind colors, custom presets write 11 hex shades (EVA-01's `eva-red` is built on the keyset red `#dd1126`). Point a status token at shade 600 in the `light` block when 500 is too light. Keep success and info apart from each other and from primary, and check badges, buttons, and `text-*` in both color modes.
- Only override tokens that differ from Nuxt UI's [defaults](https://ui.nuxt.com/docs/getting-started/theme/css-variables) (installed values: `node_modules/@nuxt/ui/dist/runtime/index.css`; color tokens are shade 500 in light, 400 in dark). Keep `DEFAULT_TOKENS` in `preview.ts` in sync, and keep `ui.colors` complete enough for `resolvePresetToken` (e.g. Aurora's `neutral: 'slate'`).
- When adding a new preset: create a `.ts` file in `theme-presets/`, export a `ThemePreset` satisfying the interface, register it in `index.ts`, and ensure `presetToCss()` generates valid CSS for all your root/headings/light/dark blocks.

## Form Architecture

- New entity forms must follow the Atomic Form + Composite Wrapper pattern: atomic forms own the field UI for one entity and accept `mode: 'standalone' | 'embedded'` with a default of `'standalone'`.
- In `standalone` mode, atomic forms may wrap themselves in `UForm`, render their own Submit/Cancel actions, and perform direct admin/edit API saves. In `embedded` mode, they must expose state through `v-model`/`update:modelValue`, hide their standalone actions, and let the parent composite own validation, navigation, and submit actions.
- Each domain's `SubmissionWizard.vue` is the composite wrapper for both create and review (`mode: 'create' | 'review'`). It owns the step slots; its paired `use*SubmissionWizard` composable owns hydration, validation, and API orchestration; navigation and footer actions come from the shared `useSubmissionWizardActions` (see "Community Submission Workflows"). Do not reintroduce flat `*SubmissionForm.vue` review composites or duplicate atomic fields.
- Define shared Zod schemas in `app/utils/schemas/` and reuse them in standalone atomic forms and wizard composables. Use `entitySelectionSchema` for existing-entity selections; keep component-local refinements only when they depend on runtime data.

### Nested submission wizards

- Wizards live in `app/components/{artisan,keyset,keyboard}/modal/SubmissionWizard.vue`, use `UStepper`, and embed the same atomic forms in create and review. Per-domain steps and review behavior are in "Community Submission Workflows".
- Maker/Profile/Brand is select-existing only and locked in review. In create mode, reusable intermediate entities (Sculpt/Keyset/Keyboard/Release) use a step-level `UTabs` toggle between `'existing'` and `'new'`, never a toggle inside an atomic form.
- Render that toggle only when options are loaded and non-empty. Treat only a successful empty response as evidence for proposing a new entity; never discard a preselected existing entity because options are empty, paginated, pending, or failed.
- Exception: the keyset step does not preload keysets. Its picker searches as the user types through `useGuardedSearch('/api/search', { term, module: 'keyset' })` (the same pattern as `KeyboardForm`'s original-keyboard picker), keeping only results whose `to` is under the selected profile and using `to` minus `/keyset/` as the `profile_keyset_id`. The Existing/New toggle is therefore always shown in create mode and never auto-switches to New. The selected option is kept in `selectedKeyset` (a direct link resolves its label via `GET /api/keysets/[profile]/[keyset]`) so its label survives new searches.
- Create mode supports repeatable Colorways/Kits/Variants. Artisan, keyset, and keyboard review each edit exactly one colorway/kit/variant (the table row) with no Add/Remove controls.
- Validate each step before advancing and validate the applicable entity/child data before saving or approving. Reuse existing create APIs in parent-to-child order; creating a Pending parent establishes ownership for subsequent child inserts.
- Selection context belongs in computed `StepperItem.description` values using selected option labels or in-progress entity names. Do not add redundant "Selected: ..." paragraphs next to pickers or repeat context inside step slots.

### Direct links and response contracts

- Detail-page links pass `maker`/`sculpt`, `profile`/`keyset`, or `brand`/`keyboard`/`release` query parameters. Jump to Colorway/Kit/Release/Variant as appropriate; derive missing profile/brand from the child's composite slug when available.
- Parent-change watchers reset dependent selections only on actual changes, never with `{ immediate: true }`. Use a separate immediate watcher for initial field synchronization (e.g. `keyset.profile_id`).
- `GET /api/keysets` returns `keysets`, not `data`. Preserve `existingKeyset.id` from direct links and submit kits through its existing-keyset endpoint rather than creating a blank keyset.
- `GET /api/makers/[maker]` returns `sculpts` keyed by ID; unwrap with `Object.values(...)` before mapping options.
- A direct "Submit a Release" link with a keyboard but no release selects `'new'` and hides the release toggle. Variant forms use a synthetic release option with ID `'draft'`, matching new variants' `release_id`; resolve the real release ID only at submit time.
- Embedded `KeysetForm` must bind `v-model:date-range` separately and convert its CalendarDate values to ISO `start_date`/`end_date` on submit. Status and Review Status remain visible; Review Status is disabled for non-moderators, read directly from the user store.

## Server and Supabase Rules

- Define API handlers with `defineEventHandler` and use H3 helpers such as `getQuery`, `readBody`, and `createError` consistently with nearby code.
- Obtain the server Supabase client with `serverSupabaseClient(event)` and the authenticated user with `serverSupabaseUser(event)`.
- `GET /api/users/:id` selects the profile row, including `appearance`. `PATCH /api/users/:id/appearance` is session-owner-only and accepts only registered theme ids and `system | light | dark`; it merges into the existing JSON value. The general `POST /api/users/:id` profile endpoint is also session-owner-only and must not accept `role` or `assignments`; admin changes use the separate admin endpoint.
- Use `requireAdminClient(event)` for admin-only server-side operations. For staff operations scoped to a specific assignment (editor/maker restricted to their assigned pages), use `getActorProfile(event)` plus `canManageAssignment`/`canManageAnyAssignment` from `~/utils/permissions` (also re-exported as `canModerateAssignment` in `server/utils/admin.ts`) instead of duplicating role checks.
- Preserve the existing middleware checks for protected pages (`app/middleware/admin.ts` for admin-only routes). For staff-but-not-admin pages, follow the existing pattern of a client-side guard (`<SharedRedirectPage v-if="!canX" to="..." />`) backed by a Pinia getter, rather than adding new route middleware.
- For insert, update, or patch payloads, use `pickTableFields(table, body)` from `server/utils/database.ts`. It validates that the body is an object and whitelists fields from generated metadata.
- Use `omitSensitive()` and existing response helpers when returning database records so internal fields such as `fts` are not exposed. It is shallow: strip nested embedded rows too (e.g. `colors.color` in `GET /api/keysets/[profile]/[keyset]`).
- Select only the columns a response uses when it is built from a few of them (e.g. `GET /api/search`, `GET /api/marketplace`, `GET /api/statistics`).
- Follow the existing pagination convention with `getQuery(event)` and Supabase `.range(from, to)`.
- Preserve existing full-text search behavior using Supabase `.textSearch()` where the endpoint already uses it.
- Artisan colorway search lives in `server/utils/colorway-search.ts` and matches colorways by their own name only (every word of the term, `deleted` excluded); maker/sculpt-only matches are left to their own palette groups. `GET /api/search` (the `KeebSearch` palette) returns the 24 most relevant colorways (`searchPaletteColorways`: exact → prefix → phrase) with `total` and `viewAllTo`, and the palette appends a "View all N artisan colorways" row when `total` exceeds the shown items. `GET /api/search/colorways?q=&page=&size=&exact=` backs the `/artisan/search` results page, ordered by maker then sculpt (`size` capped at 72), returning `{ data, total }` and an empty page with the real total when `page` is past the end; `exact=1` keeps names containing the whole term as separate words (Postgres `imatch` with `\m`/`\M`, applied through `.filter()` because the client has no `imatch` helper). The page searches as the user types (400 ms debounce, `router.replace`), keeps `q`, `page`, `exact=1`, and `group=maker` in the URL, groups the current page by maker client-side, and offers Save to Collection for signed-in users. Other palette groups stay palette-only.
- Use `createError({ statusCode, statusMessage })` for expected API errors and match nearby status codes and messages.
- Do not expose service-role credentials or bypass authorization checks from client code.
- For submitter-owned records (e.g. `artisan_colorways.submitted_by`), grant the original submitter limited edit/delete rights in addition to staff permissions, scoped by the record's status (e.g. only while still `Pending`, or not once `Approved`). Always re-check ownership and status server-side; never trust a client-supplied owner id.
- Image uploads (`server/api/images/upload.post.ts`) require staff permission via `canManageAssignment`, except the `artisan` and `keyset` module categories, which any authenticated user may upload to (community colorway/keyset submissions); the underlying record save still enforces its own permission checks.
- For schema changes, draft an idempotent SQL migration under `supabase/migrations/` for the user to review and run in the Supabase SQL editor. `supabase/` is its own repository: commit there only when asked, following `supabase/AGENTS.md`.

## Cloudflare Worker Budget

Production runs on Cloudflare Pages (Free plan: 10 ms of CPU and 128 MB per request; Error 1102 when exceeded), so keep Worker work small:

- `routeRules` in `nuxt.config.ts`: `/about`, `/changelog`, `/privacy`, and `/why-choose-keebdex` are prerendered (served as static files); private pages and tools (`/account/**`, `/admin/**`, `/notifications`, `/collection`, sort pages, submission pages, keyset `kit`/`color` editors, `/artisan/wishlist`, `/artisan/marketplace`, `/artisan/search`) are `ssr: false`. Public catalog pages keep SSR. Do not cache rendered HTML: it depends on the theme and color-mode cookies and the device. Add new private or list-heavy pages to the `ssr: false` group.
- Prerendering runs the app during the build, so the Cloudflare build needs the Supabase settings: set `NUXT_PUBLIC_SUPABASE_URL` and `NUXT_PUBLIC_SUPABASE_KEY` (plain text, both Production and Preview). `@nuxtjs/supabase` reads `SUPABASE_URL`/`SUPABASE_KEY` only at build time and bakes them into the bundle; at runtime only the `NUXT_PUBLIC_` names override it, so a build without them deploys fine and then answers every request with a 500. `NUXT_APP_SECRET` (secret, at least 32 characters) signs OG image URLs; without it `/_og/d/...` returns 500.
- Keep SSR payloads small: trim with `pick`/`transform` in `useAsyncData` (e.g. `useKeysetProfiles`, the maker list) or select fewer columns on the server.
- Icons: `@nuxt/icon` bundles every icon named in `app/` and `content/` (`icon.clientBundle.scan`, shared by SSR) and loads any other (e.g. announcement icons from the database) from the Iconify API (`provider: 'iconify'`). Never switch back to the server provider: on Cloudflare it downloads and parses whole collections (solar is 11.7 MB) inside every new Worker isolate.
- `flag-icons` CSS is imported only by `MakerForm.vue` and `BrandForm.vue`, and its SVGs are emitted as files (`vite.build.assetsInlineLimit`); imported globally it added ~420 kB of inline CSS to every SSR response.

## Community Submission Workflows

Signed-in users can propose artisan colorways, keyset kits, and keyboard variants; staff review them before they become public. Every domain uses the same pieces:

- **Routes**: create at `/{domain}/submissions/submit`, review at `/{domain}/submissions` (`artisan`, `keyset`, `keyboard`), both linked from the module's sidebar section in `app/layouts/default.vue` behind `authenticated.value`. Public create/contribute buttons route to the submit page; standalone modals are only for admin CRUD and sub-entity quick edits. Detail-page "Submit a …" links pass the query params described in "Direct links and response contracts".
- **UI**: `SubmissionWizard.vue` + its `use*SubmissionWizard` composable handle both create and review. Review pages are `UTable`s with a status filter (`statusOptions` / `statusColorMap` from `app/utils/index.ts`), scoped to the submitter or to staff for the relevant assignment: artisan lists one row per colorway, keyset and keyboard one expandable row per parent (see "Review flow").
- **Shared client pieces** (extend these instead of copying per domain):

### Create flow

- Picking an existing, published (null/Approved) sculpt/keyset/keyboard lets any signed-in user add colorways, kits, or releases/variants to it without creating or re-moderating the parent. The proposal is stored `Pending` and is visible only to its submitter and staff.
- Proposing a new parent creates it first (`Pending`, owned by the submitter), which satisfies the RLS ownership needed for the child inserts that follow. The wizard calls the existing single-entity endpoints sequentially; do not describe these multi-write flows as atomic.

### Review flow

- Artisan review rows are single colorways with their maker and sculpt. Keyset and keyboard review are grouped by parent: `GET /api/submissions/keyset` returns `{ data: [{ profile_keyset_id, keyset, kits }], count }` and `GET /api/submissions/keyboard` returns `{ data: [{ brand_keyboard_slug, keyboard, variants }], count }`, where `count` and `page`/`size` refer to groups (ordered by their newest matching leaf) and each group holds every leaf of that parent matching the status filter. The pages render one expandable `UTable` row per group (expanded state keyed by the parent key via `getRowId`) with a nested leaf table carrying the per-leaf actions below, plus moderator-only Approve All / Reject All for the group's `Pending` leaves and Delete All for its `Rejected` leaves the user may delete (moderators, or the submitter's own), all behind `SharedConfirmModal` (`confirmColor` sets the confirm button color), except Reject All, which uses `SharedNoteModal` to collect the reject note; bulk actions send each leaf sequentially to its endpoint (POST to moderate, DELETE to `${leafUrl}/${id}`) so the parent cascade sees every prior result. Row actions: Edit (opens the review wizard with `mode="review"` and `:submission`), moderator-only Approve/Reject (each hidden when the row already has that status; Reject asks for a note in `SharedNoteModal`), and Delete (moderators, or the submitter while the row is Pending/Rejected) behind `SharedConfirmModal`. Toasts name the row and use the `approve` / `reject` / `delete` actions of `successToast`.
- The wizard edits exactly one leaf (no Add/Remove). Parent levels (sculpt, keyset, keyboard, release) are editable only while under review (Pending/Rejected, or a status-less release following its Pending keyboard) and render as locked summaries once published. Footer actions (`SharedSubmissionWizardFooter`): Back, Save Changes (submitter), Save & Approve (moderator), Delete.
- Save & Approve saves each parent still under review (keyboard → release, then the leaf) and then the leaf with `action: 'approve'`; approval of the parents rides on the leaf save. Row Approve/Reject post `{ id, action }` (plus the required `note` when rejecting) to the leaf's existing endpoint (save endpoints normalize only the keys present, so a sparse body never blanks other columns); there are no `/api/submissions/{domain}/[id]` endpoints, only the three list endpoints and the two create endpoints above.
- Server-side cascade (`cascadeSculptReview`, `cascadeKeysetReview`, `cascadeKeyboardReview`): approving a leaf approves its Pending/Rejected parents (status-less sibling kits, or other status-less releases and all status-less variants of the keyboard, are first set to `Pending` under the parent's submitter so they stay in the queue instead of being published unreviewed); rejecting a leaf rejects a Pending parent only once none of its children is still alive. Deleting the last leaf of a parent under review deletes that parent (variant → release → keyboard), so no orphan Pending parents remain.
- A submitter editing their own `Rejected` leaf/parent resets it to `Pending` (server-side), and the page switches its filter to Pending via `onSuccess({ resubmitted })`. Resubmitting a kit or colorway also resubmits its `Rejected` keyset or sculpt (`resubmitRejectedParent`); keyboard and release parents are resubmitted by their own saves, which the review wizard sends before the variant.

### Shared server contract (`server/utils/child-submissions.ts`, `server/utils/submission-queue.ts`)

- Kit, release, variant, and colorway endpoints call `getChildSubmissionContext(event, domain, parentKey)` (parent keys: `profile_keyset_id`, `brand_keyboard_slug`, `maker_sculpt_id`). Client moderation fields are always stripped (`omitModerationFields`) and re-applied by `attribute()`: official parent + staff → `Approved` with `verified_*`; otherwise `Pending` owned by `auth.uid()`. Keyset kits, keyboard variants, and artisan colorways always carry their own status; keyboard releases only when the parent keyboard is published, otherwise they follow their Pending keyboard.
- Staff may send `action: 'approve' | 'reject'` (`getModerationOverride`, built on `getReviewPatch`); non-staff get 403. New records get their moderation columns from `getSubmissionAttribution(isStaff, userId)`; resubmission after rejection uses `getOwnResubmission()` / `getResubmissionPatch()`.
- Parent save endpoints (`POST /api/keysets/[profile]/[keyset]`, `/api/keyboards/[brand]/[keyboard]`, `/api/makers/[maker]/sculpts/[sculpt]`) never trust client moderation fields from non-staff: they are stripped, and only the submitter's own `Rejected` row is resubmitted as `Pending`. Staff edits through the admin forms keep the fields they send.
- Child saves and deletes go through `updateChildSubmission` (resubmission + 403 when RLS refuses), `resubmitRejectedParent`, `deleteChildSubmission`, and `deleteParentIfEmpty`; the three cascades share `resolveParentReview`. Updates and deletes must check the affected row count: RLS filters silently, so return a 403 with a message when nothing changed.
- List endpoints use `getReviewQueueContext` (actor, assignment scope, page/size, whitelisted status via `parseReviewStatus`); the grouped keyset and keyboard queues are both `listGroupedSubmissions` configurations. `inFilter` quotes values inside PostgREST `or()` filters.
- Release and variant saves normalize numbers, optional strings, and material arrays with `normalizeFields` (`server/utils/index.ts`); empty arrays are stored as `null`.
- `GET /api/keysets/[profile]/[keyset]` lists only official kits (null/Approved); kits under review are reachable only through the review queue. `GET /api/keyboards/[brand]/[keyboard]` still returns releases/variants under review because the keyboard wizard needs them, so the public keyboard page filters out non-official releases and variants client-side.
- Artisan colorways use `review_status` like every other table (the former `status` column was renamed); sculpt proposals live in `artisan_sculpts` and have no separate queue.

### Database & RLS conventions for submissions

- A table that supports submissions needs the four control columns, added through a migration under `supabase/migrations/` (never by hand-editing generated types).
- Target RLS: public reads Approved/null rows; submitters read their own Pending/Rejected rows; authorized staff read and manage their scope. Non-staff inserts must be `Pending`, attributed to `auth.uid()`, with null `verified_*`; only staff may insert null/approved rows or change moderation fields. Submitters update their rows while `Pending` (also `Rejected`, which resubmits as `Pending`) and delete while `Pending`/`Rejected`, never `Approved` or `null`.
- Child tables combine the parent's state (via `exists` subqueries) with their own: community inserts need an official parent, or the submitter's own Pending parent (kits → own Pending keyset; variants → own Pending keyboard plus an official release or own Pending release). Staff scope comes from `can_manage` (keyset: `profile_keyset_id`; keyboard: the parent's `brand_slug`, not the child's column; artisan: `maker_id`). Never broaden child INSERT permissions without controlling visibility and moderation. Verify the deployed policies; local migration drafts are not proof they are applied.

### Auto-approve rule for staff submissions

- When the actor is staff for the relevant assignment (`canManageAnyAssignment(profile) && canManageAssignment(profile, assignment)`: `brand_slug`, `profile_keyset_id`, `maker_id`), creates through the shared endpoints (`/api/submissions/*`, and the kit/release/variant/colorway create endpoints used by admin and community forms) are written as `Approved` with `verified_by = user.sub` and `verified_at = new Date().toISOString()` in the same insert. Non-staff always get `Pending` with null `verified_*`.
- Parent save endpoints used by the admin forms (`POST /api/keysets/[profile]/[keyset]`, `/api/keyboards/[brand]/[keyboard]`) write staff bodies as sent, so admin-created records stay implicitly approved via `null` unless a moderator sets Review Status. Non-staff writes through them are forced to `Pending` (create) or keep their status apart from resubmission (update), as described in "Shared server contract". Sculpts always get attribution from `getSubmissionAttribution`.

### Delete cascade rule for submissions

- Delete children before the parent while parent-scoped RLS still applies, using the per-item delete endpoints (never a published parent): keyboard variants → releases → keyboard; keyset kits → keyset; artisan colorways → sculpt. Check every delete result instead of relying on `ON DELETE CASCADE`.
- Delete rights belong to authorized staff or the owner of a `Pending`/`Rejected` submission; never to an owner of an `Approved` or `null` record.

### Toast messages

Every toast has a short Title Case title (like HTTP status text: `Not Found`, `Session Expired`) and a full-sentence description. Build toasts with the helpers in `app/utils/toast.ts` (auto-imported) and pass the result to `useToast().add()`; do not hand-write success/error toast objects. `successToast(action, { entity, name, target })` covers record changes with a fixed set of actions: `add` (create, or add to a collection via `target`), `update`, `delete` (permanent), `remove` (take out of a collection), `move`, `approve`, `reject`; it renders a Title Case title (`Kit Added`) and a sentence description (`Kit "Base" has been added.`); pass `scope` for the parent of bulk results and `plural` for plural entity names that are not counted labels. Use `countLabel(n, 'kit')` as the `entity` for bulk results; the count appears only in the description (`3 kits in "GMK Olivia" have been approved.`), while the title drops it (`Kits Approved`). `notificationToast(view)` turns a rendered notification into a toast with a _View_ action. `noticeToast(key)` covers fixed app events that are not record changes (clipboard, sign-out, pins, sort order, feedback, `submission_pending`, `color_fetched`, `already_in_collection`); add a key there instead of an inline toast. `validationToast(message, title?)` is for client-side checks and shows the message verbatim as the description (default title `Invalid Input`); never route validation through `errorToast`. `errorToast(error, { showOriginalMessage })` is for caught errors: it logs and maps by status, and `showOriginalMessage` shows the server `statusMessage` as the description (use it where endpoints return user-facing messages, as the submission flows do).

Site-wide news lives in the database as announcements (see "Announcements"), never as toasts written in code. The only hard-coded notice is the cookie consent (`useCookieConsent()`): `app/layouts/default.vue` adds the announcement toasts and then the consent on mount, through one `useToast()` instance (`showToasts(toast)`, `show(toast)`). The toaster measures each toast once on mount to lay out the stack, and every `useToast()` call has its own add queue, so toasts added through several instances can mount in the same tick, get measured at the collapsed height, and overlap when the stack expands; never reorder `toasts` either, since the toaster's ref order would no longer match. The app toaster is `{ max: 5, expand: false }` (`app/app.vue`).

## Notifications

Users are notified when staff review or delete their submissions, resolve their feedback, or change their role; the moderator who rejected a submission hears when it is resubmitted. Site-wide announcements are separate (see "Announcements").

- **Creation**: only Postgres triggers create notifications, through `push_notification(user, type, actor, entity_type, entity_id, data, preference, group_key)` (security definer, not callable by clients). It skips the actor's own actions and preferences the recipient turned off, and merges a notification into the recipient's unread one with the same `group_key` from the last 15 minutes (`data.count`, moved to the top). `notifications` RLS: users read, delete, and update `read_at` on their own rows; no insert. RPCs: `unread_count()`, `mark_all_notifications_read()`. Migrations (idempotent, run in order in the SQL editor): `20261010000000_notifications` (table, preferences, `push_notification`, account trigger), `20261010000100_submission_notifications`, `20261010000200_feedback_notifications`.
- **Submissions**: `keyset_kits`, `keyboard_variants`, and `artisan_colorways` have `review_note` (≤ 280). `guard_submission_review` lets only staff approve/reject or write the note and requires a note to reject; `submission_details()` builds the shared `data` (`domain`, `entity`, `parent_key`, `parent_name`, `submission_name`). Triggers send `submission_status` (grouped by parent, status, and note), `submission_resubmitted` to the moderator who rejected the row (`OLD.verified_by`) on the submitter's `Rejected → Pending` edit, and `submission_deleted` when someone other than the submitter deletes a Pending/Rejected row. Delete endpoints accept an optional staff `{ note }` (`deletionNoteSchema`), saved to `review_note` before deleting so the trigger can send it. Parents never notify. Reject posts `{ id, action: 'reject', note }`; `getModerationOverride` validates it with `reviewNoteSchema`.
- **Account**: changing a user's `role` or `assignments` (by someone else) sends `account_role_changed` with the added and removed assignments. It has no preference key, so it is always delivered.
- **Feedback**: the `attribute_feedback` trigger sets `feedbacks.submitted_by` from `auth.uid()`, so signed-in authors only write a message and admins read their name and email from `users`; guests type a name and an optional email. `POST /api/admin/feedbacks/[id]` takes `{ resolved, note? }` (`resolutionNoteSchema`); resolving sends `feedback_resolved` (`data`: `message` excerpt, `note`) to signed-in authors. RLS: anyone inserts unresolved feedback attributed to themselves; only admins read and update.
- **Notes**: `SharedNoteModal` collects staff notes (counter at 280; required unless `optional`). Reject requires one; Resolve takes an optional comment (reads Resolve with Comment once there is text); deleting someone else's submission takes an optional reason.
- **API** (`server/api/notifications/`): `GET /` (`before`, `unread`, `limit` ≤ 50) → `{ data, hasMore, unread }`, `GET /unread-count`, `PATCH /:id` `{ read }`, `DELETE /:id`, `POST /read-all`, `GET` / `PATCH /preferences`.
- **Client**: `app/utils/notifications.ts` is the registry (`renderNotification`: title, description, `quote`, `note`, icon, color, link). `useNotifications()` shares state and optimistic actions with rollback; `plugins/notifications.client.ts` subscribes to realtime INSERT/UPDATE for the user, toasts inserts (grouped updates only refresh the row), refreshes on tab focus, and resets on sign-out. `/notifications` has two tabs, Notifications and Announcements (each with its unread badge), and an Unread / All filter (`UTabs`) for the open tab, Unread by default (`?tab=announcements&filter=all`; the old `?filter=announcements` still opens Announcements), plus day groups, Load older, Mark all as read next to the first day group (when the open tab has unread items), an empty-state Show All action under Unread, and rows built on `NotificationRow` (shared with announcements: icon, title with unread dot and time, description, extra content, a link button below, hover actions): a View button below goes to the target and marks read; hover reveals read/unread and delete; rows themselves don't navigate.
- **Preferences**: `notification_preferences (user_id, preference, enabled)`; a missing row means on. Keys and groups live in `app/utils/notification-preferences.ts` and drive `/account/settings/notifications` (groups in order Announcements, Submissions, Feedback; a switch per key, saved immediately, with the item's `icon`/`color` (matching its notification) in multi-item groups; `staffOnly` items such as Submissions → Resubmitted show only to staff, and a group with no visible items is hidden). `announcement_toasts` (Announcements group) is not a notification type: `GET /api/announcements` reads it to turn announcement toasts off.
- **Adding a type**: add a renderer, a preference key (unless it must always be delivered, like `account_role_changed`), and a trigger calling `push_notification()` with that key.

## Announcements

Admins publish site-wide announcements without a deploy. They show as toasts on every page (added once per page load by the layout) and in the Announcements tab of `/notifications` (signed-in users). Migration `20261011000000_announcements` (after the notification migrations); `supabase/seed/announcements.sql` holds the announcements that used to be hard-coded toasts and must also run in production.

- **Tables**: `announcements` (`key` primary key, also the toast id and the dismissal key, never changed after creation; `title`, `description`, `icon`, `color`, optional `cta_label` + `cta_url` together, `show_toast`, `audience` `all | guest | signed_in | mods`, `priority` (higher first), `starts_at`, `ends_at`). Check constraints mirror `app/utils/schemas/announcement.ts`: `cta_url` is `https://` or an internal path (`/x`, not `//x`), no whitespace. `announcement_dismissals (user_id, announcement_key, dismissed_at)` cascades on delete.
- **RLS**: anyone, guests included, reads live announcements (`starts_at <= now() < ends_at`), except `mods`, readable only by `can_manage_any()` (mirrors `canManageAnyAssignment`); admins read all rows and are the only writers. Users read and insert their own dismissals, and only for announcements they can see. RPCs (security invoker): `dismiss_announcement(key)`, `merge_dismissals(keys)` (skips unknown or hidden keys). `unread_count()` stays personal-only.
- **API**: `GET /api/announcements` → `{ data, signedIn, userId, dismissed, toasts }`; guests get `all`/`guest`, signed-in users everything but `guest` (RLS removes `mods` for non-staff). `POST /api/announcements/[key]/dismiss`, `/merge-dismissals` `{ keys }`, `/seen`. Admin: `GET` / `POST /api/admin/announcements`, `POST` / `DELETE /api/admin/announcements/[key]` (update is a patch; unpublish sends `ends_at`). Bodies are validated by `announcementSchema` / `announcementPatchSchema`, which also act as the field whitelist, and constraint errors map to 400/409.
- **Client**: `useAnnouncements()` (shared state; `load()` is latest-wins and every caller resolves with the latest result). Dismissed and read are the same thing. Guests: this device's `dismissed-announcements` localStorage list plus legacy `acknowledged` values (localStorage or cookie) stored under an announcement's key by the old toasts. Signed in: `announcement_dismissals` is the source of truth, plus this device's keys not yet merged for that user (`announcement-dismissals-merged:<uid>`), so clearing the table shows announcements again. Dismissing writes the server when signed in (and the device list, marked as merged) or the device list for guests. `plugins/announcements.client.ts` merges this device's keys once per user on sign-in, then loads announcements (for the sidebar badge) and refreshes them when the tab becomes visible. On mount, the layout (`app/layouts/default.vue`) shows up to `ANNOUNCEMENT_TOAST_LIMIT` (3) toasts by priority plus a "+N more updates" toast (to the Announcements tab, or `/changelog` for guests) when there are more, then the cookie consent. The layout stays mounted across navigation, so they show once per page load, whatever the first page. When the stack expands, announcements sit 8px apart instead of the toaster's 16px (`ANNOUNCEMENT_STACK_CLASSES`, a `translate-y` that adds to the toaster's `transform`, recomputed as toasts land or are dismissed), so they read as one group between the cookie consent and the summary. Announcement toasts (and the summary) hide after the toaster's default duration and come back on the next page load; only the CTA or Dismiss records the dismissal. They have no close button, since closing would look like dismissing. Toast builders and helpers live in `app/utils/announcements.ts`.
- **Tab**: `/notifications?tab=announcements` lists every live announcement (read ones too), grouped by day like notifications and newest first (priority only orders toasts), with `NotificationAnnouncementItem` on `NotificationRow`: the CTA is the button below. Unread = not dismissed; the tab badge and the sidebar badge count them. Mark as read (hover, unread only) or the CTA dismisses one; Mark all as read dismisses every unread one. Reading is one-way (no Mark as unread). Announcements never mix into the Notifications tab; the All / Unread filter applies to both tabs.
- **Admin**: `/admin/announcements` (Management menu) lists scheduled, live, and ended announcements with Preview Toast, Edit (`ModalAnnouncementForm`, with a tab-item preview), Unpublish, and Delete.

## Git and Documentation

Commit messages follow Conventional Commits through commitlint. Write user-facing notes for unreleased changes in `content/changelog/unreleased.md` (a bold-led summary paragraph, then What's New / Bug Fixes / Improvements; create the file with `title: Unreleased` frontmatter when it is missing); `CHANGELOG.md` only points there. To cut a release, run `bun run release <version> "<name>" [--prerelease]` (turns `unreleased.md` into `content/changelog/v<version>.md` with version, name, and date, keeps its `authors` or credits the `gh` user when it has none, and bumps `package.json`), commit it as `chore(release): v<version>`, push, then run `bun run release:publish <version>`, which creates the GitHub release (tag `<version>`, title `v<version> - <name>`, the format of every existing release) from that file, or updates it when it already exists. GitHub releases are copies of the files, never the source. Do not create commits, branches, or pull requests unless explicitly requested; writing the PR notes file described below is not a commit.

Release notes are read by collectors, not developers. Keep every release in the same shape:

- **Summary**: one short paragraph that opens with a bold phrase tied to the release name (e.g. "Throw the **doors open** —" for _Open Doors_), then names the two or three biggest changes.
- **Sections**, in this order and only when they have entries: `### ✨ What's New`, `### 🐛 Bug Fixes`, `### 🚀 Improvements`, then `### ⚠️ Breaking Changes` for changes users notice (renamed pages, moved addresses). Never write "None".
- **Entries**: a full, natural sentence each (two when needed), describing what users see or can now do and why it helps, in the present tense, ending with a period. Avoid clipped fragments that read abruptly ("Images load faster."); say enough to give context ("Grids load images sized for your screen, so pages load faster, especially on phones."). Bold the feature name when it leads the entry; italicize UI labels (_Save_, _Group Buys_).
- **Length**: there is no fixed number of entries; a big release can be long. What must not happen is overlap: merge entries that describe the same feature or area (e.g. several keyset page fixes) into one, and describe a large change once, in What's New, instead of again under Improvements.
- **Leave out** internal work users never see: composables, refactors, table or column names, lint and dependency updates, RLS or API fixes without a visible symptom. Do not list every label, route, or option; name the feature and its benefit.
- **Names**: release names are short and evocative, two or three words without a leading article, matching the theme of the release (_First Keystroke_, _Keyboard Era_, _Aurora Borealis_, _Open Doors_).
- **Authors**: keep `anhthang` first; add Claude as a co-author (`name: Claude`, `icon: simple-icons:claude`, `color: '#D97757'`, `to: https://claude.com/claude-code`) when Claude worked on the release.
- Before cutting a release, reread `unreleased.md` against these rules: entries added change by change tend to grow too long and to repeat each other.
