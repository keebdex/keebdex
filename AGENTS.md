# Keebdex Agent Instructions

This is the canonical instruction file for every AI coding agent working in this repository (Claude Code, OpenAI Codex, Cursor, GitHub Copilot, and others). Keep it as the single source of truth: `CLAUDE.md` imports it, and `.github/copilot-instructions.md` points here. Update this file instead of creating agent-specific copies. A tool-specific file only points here and holds what is specific to that tool; it is never a bare `@AGENTS.md` line, but says in a sentence where the shared instructions live and how the tool loads them.

## Project Overview

Keebdex is a Nuxt 4 application for keyboard collectors. It uses Vue 3, TypeScript, Nuxt UI, Tailwind CSS, Pinia, Nuxt Nitro/H3, and Supabase PostgreSQL.

Use Bun for local commands. The repository contains a `bun.lock` file.

## Quick Start for Agents

1. Read this file, then the task plan in `.ai/plan/` if one applies.
2. Locate the closest existing pattern (same domain, same kind of file) and follow it before inventing a new one.
3. Keep the diff focused. Do not refactor unrelated code or touch generated files.
4. Verify with the narrowest relevant check first (see "Formatting and Validation"), and report only the checks that actually ran.
5. Do not commit, branch, or open a PR unless the user asks (see "Git and Documentation").

## Important Commands

- `bun run dev`: start the Nuxt development server. The `predev` hook generates database field metadata first.
- `bun run build`: build for production. The `prebuild` hook generates database field metadata first.
- `bun run generate`: generate the static site; this also runs the metadata generation hook.
- `bun run generate:table-fields`: regenerate `server/utils/table-fields.generated.ts` from the database types.
- `bunx eslint .`: run ESLint. Use `bunx eslint . --fix` for automatic fixes; there is currently no `lint` script in `package.json`.
- `bun run preview`: preview a production build.

There is no test script or test suite currently defined in `package.json`. Do not claim tests passed unless a relevant check was actually run.

## Vue and Nuxt Conventions

- Follow the existing Vue 3 Composition API style with `<script setup>`.
- Keep Vue single-file component blocks in this order: `<template>`, then `<script setup>` (or `<script>` when required), then `<style>`.
- Use TypeScript for new application code unless the surrounding file is intentionally JavaScript.
- Build URL slugs (sculpt, keyset, keyboard, maker, and brand slugs, download filenames) with `urlSlugify` (`app/utils/slug.ts`, import it explicitly on the server), never `slugify` directly: it drops punctuation (`'`, `.`, `:`, `+`) the same way catalog-sync's `urlSlugify` does, so synced and app-made slugs match. Colorway ids are the exception: `colorways.post.ts` hashes a plain `slugify` slug into `colorway_id`, and changing it would change existing ids.
- lodash is not a dependency: use native JavaScript or `es-toolkit` for array and object helpers. Import `sortBy` from `es-toolkit/compat`, which keeps lodash behavior (nested paths such as `'artisan.maker_id'`, several keys, `null` last); take the rest (`groupBy`, `keyBy`, `omit`) from `es-toolkit` with a key callback, since its main entry does not accept key strings.
- Keep components in PascalCase. Keep variables and functions in camelCase. Use snake_case for database identifiers.
- Keep domain-specific components in their existing domain folders; put genuinely reusable components in `app/components/shared/`.
- Prefer existing Nuxt UI components and the established slots/configuration over custom replacements, e.g. `UPageCard` and `UUser` with the theme's rounding instead of hand-built cards.
- Use `NuxtImg` for optimized images where appropriate. The default image provider (`app/providers/cloudflare-images.ts`, registered as `cloudflare`, which overrides @nuxt/image's built-in Image Resizing provider of that name; it must stay the default because presets cannot set a provider) turns stored Cloudflare Images URLs of Keebdex's own account (`cloudflareImageBase` in `app/utils/image-info.ts`, which compares the URL's hash with `runtimeConfig.public.cloudflare.accountHash`; `…/<id>/public`, ids may contain slashes) into flexible variants (`…/<id>/w=<n>,fit=scale-down`, width rounded up to a fixed ladder) whenever `sizes` applies, and returns every other source unchanged, including images on other Cloudflare accounts (vendor sites), which answer flexible variants and `format=json` with a 403 until catalog-sync copies them over. Give images a preset from `nuxt.config.ts` (`square` for artisan colorway and sculpt grids, `cover` for keyset and keyboard grids and the related keyboards drawer, `thumb` for submission thumbnails) or a `sizes` of their own for other layouts (the keyset detail cover, the marquee); preset sizes are measured shares of the viewport, so re-measure them when a grid's columns change. Grid and thumbnail images also take `loading="lazy"` and `decoding="async"`; the above-the-fold keyset detail cover loads eagerly with `fetchpriority="high"` instead. Leave images captured by `SharedSnapshot` or opened in previews on the stored URL. Brand, maker, and profile logos (`logoUrl(key)` in `app/utils/logo.ts`, `${imgUrl}/logo/<key>.png`; server code passes its own `imgUrl` as the second argument) are fixed 500×500 files on R2, not Cloudflare Images, so they never get a preset. The `keebdex` bucket's CORS rule allows `GET`/`HEAD` from `https://keebdex.org`, `https://www.keebdex.org`, and `http://localhost:3000`, so captured images (`SharedSnapshot`, `captureScreenshot`) can include logos; another origin's capture drops them.
- Cards with an image above the title (`UPageCard` with `reverse`) use `imageCardContainerClass` (`app/utils/index.ts`) as their `container`, which pins the grid column to the card so footer actions cannot widen it; footers wrap (`pageCard.slots.footer` in `app/app.config.ts`), and a custom action row inside the footer needs its own `flex-wrap`. Artisan grids use `artisanGridClass`.
- Empty states use `UEmpty` (naked by default; Carbon overrides it to `subtle`) with an `icon`, a Title Case `title`, a one-sentence `description`, and `actions` for a next step. Keep `UPageSection` / `UPageCTA` for content sections and calls to action (e.g. `SharedProtectedPage`). In-page view switchers in the toolbar `UNavigationMenu` take icons or not per page, whichever reads better there (e.g. the `/notifications` tabs have icons).
- Follow the existing mobile-first Tailwind styling and the design tokens in `app/app.config.ts` and `app/assets/main.css`.
- Use the centralized icon names configured in `app/app.config.ts` rather than introducing arbitrary icon sets.
- Do not pass props that repeat a component's configured default. `UButton` and `UBadge` default to `color: 'neutral'` and `variant: 'soft'` (`app/app.config.ts`), so never write `color="neutral"` on them. Check the theme presets before treating a prop as a default: Carbon sets the button and badge `variant` to `solid`, so an explicit `variant="soft"` stays where soft is wanted in every theme.
- Buttons with an icon hide their label below `md` (`app/app.config.ts`). Pass `ui: { label: 'block' }` (or use the default slot) when the text must stay visible on phones, e.g. empty-state actions.
- Copied/downloaded images must not depend on the screen size. Render what is captured inside `SharedSnapshot` (off screen, client-only, rendered only while capturing, optional fixed `width`, waits for images) and call its exposed `capture()`; content with its own fixed size (the cards in `ArtisanColorwayCard`'s popup: the theme-styled `ArtisanColorwayShareCard`, as wide as the 380×550px trading cards: _Keebdex Simple_ by default, only the photo and a one-line `colorwayTitle`, or _Keebdex Detailed_, 550px tall with the photo taking what the text leaves; the maker's logo is the avatar of the title and badges, and it signs off on the right with `AppWordmark domain`, which spreads `org` under _dex_ after the bar) may be captured in place. Use the helpers in `app/utils/screenshot.ts`: `captureScreenshot`, `copyBlob` (pass the capture promise so the clipboard write stays in the click gesture, as Safari requires), `downloadBlob`, `shareBlob`/`canShareFiles`. Current users: the wishlist sheet, and `KeyboardVariantCard` (48rem, renders itself with `snapshot`; its `SharedSpecList` lays out by container width, so the image keeps three columns on any screen).
- Signed-out gates use `SharedProtectedPage` (`icon`, `title`, `description`, optional `features`, `navTitle` for the mobile navbar, and `signInLabel`).
- Users' profile pictures (Google or Discord) go through `userAvatar(src, name)` (`app/utils/index.ts`), which loads them with `referrerpolicy="no-referrer"`: Google refuses most avatar requests that carry a referrer once a page shows several.
- Invert dark logos with the Tailwind `dark:invert` class (e.g. `ui.image: invertible && 'dark:invert'`), never with a `useColorMode().value === 'dark'` check: with a `system` preference SSR cannot know the mode and the class mismatch is not patched on hydration.

## Form Architecture

- New entity forms must follow the Atomic Form + Composite Wrapper pattern: atomic forms own the field UI for one entity and accept `mode: 'standalone' | 'embedded'` with a default of `'standalone'`.
- In `standalone` mode, atomic forms may wrap themselves in `UForm`, render their own Submit/Cancel actions, and perform direct admin/edit API saves. In `embedded` mode, they must expose state through `v-model`/`update:modelValue`, hide their standalone actions, and let the parent composite own validation, navigation, and submit actions.
- Each domain's `SubmissionWizard.vue` is the composite wrapper for both create and review (`mode: 'create' | 'review'`). It owns the step slots; its paired `use*SubmissionWizard` composable owns hydration, validation, and API orchestration; navigation and footer actions come from the shared `useSubmissionWizardActions` (see `docs/agents/submissions.md`). Review reuses the wizard and its atomic forms; there is no separate review form.
- Atomic forms double as the Suggest Edit form (`SharedSuggestionForm`, see `docs/agents/edit-suggestions.md`): a field added to a form becomes suggestable automatically, so only fields a suggestion must never change need hiding behind the form's `suggest` prop (and listing as protected).
- Define shared Zod schemas in `app/utils/schemas/` and reuse them in standalone atomic forms and wizard composables. Use `entitySelectionSchema` for existing-entity selections; keep component-local refinements only when they depend on runtime data.

### Nested submission wizards

- Wizards live in `app/components/{artisan,keyset,keyboard}/modal/SubmissionWizard.vue`, use `UStepper`, and embed the same atomic forms in create and review. Per-domain steps and review behavior are in "Community Submission Workflows".
- Every step above the reviewed item renders through `SharedSubmissionEntityStep` (`label`, `reviewed`, `v-model:selected` / `v-model:entity-mode`, `tabs` when there is something to pick, `options` or a `select` slot such as the keyset search, the entity's form in the default slot; in review the form while `under-review`, else the published `name` and `to`). Step 1 (Maker/Profile/Brand) is driven by `useSubmissionOwner(domain, selected, onNew)` (its `stepProps` bind to the step; `onNew` switches the next step to new): an existing one (published, plus the caller's own proposals through `?own=1`) or a new one proposed in `MakerForm` (`suggest`), `KeysetModalProfileForm`, or `BrandForm`, created first on submit by `ensure()` (its key is the form's slug or `urlSlugify(name)`). A proposed owner has nothing to pick under it. In review it is locked once published and shows its form again while under review (`load`, `save` before the rest). In create mode, the other reusable intermediate entities (Sculpt/Keyset/Keyboard/Release) also use a step-level `UTabs` toggle between `'existing'` and `'new'`, never a toggle inside an atomic form.
- Render that toggle only when options are loaded and non-empty. Treat only a successful empty response as evidence for proposing a new entity; never discard a preselected existing entity because options are empty, paginated, pending, or failed.
- Exception: the keyset step does not preload keysets. Its picker searches as the user types through `useGuardedSearch('/api/search', { term, module: 'keyset' })` (the same pattern as `KeyboardForm`'s original-keyboard picker), keeping only results whose `to` is under the selected profile and using `to` minus `/keyset/` as the `profile_keyset_id`. The Existing/New toggle is therefore always shown in create mode and never auto-switches to New. The selected option is kept in `selectedKeyset` (a direct link resolves its label via `GET /api/keysets/[profile]/[keyset]`) so its label survives new searches.
- Create mode supports repeatable Colorways/Kits/Variants. Artisan, keyset, and keyboard review each edit exactly one colorway/kit/variant (the table row) with no Add/Remove controls.
- Validate each step before advancing and validate the applicable entity/child data before saving or approving. Reuse existing create APIs in parent-to-child order; creating a Pending parent establishes ownership for subsequent child inserts.
- Selection context belongs in computed `StepperItem.description` values using selected option labels or in-progress entity names. Do not add redundant "Selected: ..." paragraphs next to pickers or repeat context inside step slots.

### Direct links and response contracts

- Detail-page links pass `maker`/`sculpt`, `profile`/`keyset`, or `brand`/`keyboard`/`release` query parameters. Jump to Colorway/Kit/Release/Variant as appropriate; derive missing profile/brand from the child's composite slug when available.
- Parent-change watchers reset dependent selections only on actual changes, never with `{ immediate: true }`. Use a separate immediate watcher for initial field synchronization (e.g. `keyset.profile_id`).
- `GET /api/keysets` returns `keysets`, not `data`. Preserve `existingKeyset.id` from direct links and submit kits through its existing-keyset endpoint rather than creating a blank keyset.
- `GET /api/makers/[maker]` returns `sculpts` keyed by ID; unwrap with `Object.values(...)` before mapping options.
- A direct "Add Release" link with a keyboard but no release selects `'new'` and hides the release toggle. Variant forms use a synthetic release option with ID `'draft'`, matching new variants' `release_id`; resolve the real release ID only at submit time.
- Embedded `KeysetForm` must bind `v-model:date-range` separately and convert its CalendarDate values to ISO `start_date`/`end_date` on submit. It hides its Profile field (step 1 picks the profile, a proposed one included, and the wizard syncs `profile_id`); with `colors` (create mode) it shows _Colors_, which the wizard saves after creating the keyset (`POST /api/keysets/[profile]/[keyset]/colors`). Status and Review Status remain visible; Review Status is disabled for non-moderators, read directly from the user store.

## Server and Supabase Rules

- Define API handlers with `defineEventHandler` and use H3 helpers such as `getQuery`, `readBody`, and `createError` consistently with nearby code.
- Obtain the server Supabase client with `serverSupabaseClient(event)` and the authenticated user with `serverSupabaseUser(event)`.
- `GET /api/users/:id` selects the profile row, including `appearance`. `PATCH /api/users/:id/appearance` is session-owner-only and accepts only registered theme ids and `system | light | dark`; it merges into the existing JSON value. The general `POST /api/users/:id` profile endpoint is also session-owner-only and must not accept `role` or `assignments`; admin changes use the separate admin endpoint.
- Use `requireAdminClient(event)` for admin-only server-side operations. For staff operations scoped to a specific assignment (editor/maker restricted to their assigned pages), use `getActorProfile(event)` plus `canManageAssignment`/`canManageAnyAssignment` from `~/utils/permissions` (also re-exported as `canModerateAssignment` in `server/utils/admin.ts`) instead of duplicating role checks.
- Preserve the existing middleware checks for protected pages (`app/middleware/admin.ts` for admin-only routes). For staff-but-not-admin pages, follow the existing pattern of a client-side guard (`<SharedRedirectPage v-if="!canX" to="..." />`) backed by a Pinia getter, rather than adding new route middleware.
- Makers and profiles are keyed by text: `artisan_makers.maker_id` and `keyset_profiles.profile_id` (the slugs in URLs, logo file names, and assignments, and the primary keys the children's `maker_id` / `profile_id` point at). Their `id` is a numeric identity column like every other catalogue table's, which nothing writes (`pickTableFields(..., ['id', 'maker_id'])` in the maker save, which keys on the route param); never read `maker.id` or `profile.id` as a slug. Brands follow the keyboard module's naming instead: `id` plus `slug`. The key changes only while the record is under review (a reviewer fixing a proposed slug, `rename()` in `useSubmissionOwner`); once published it is the address, the logo file, assignments, pins, and what catalog-sync writes, so `saveOwnerSubmission` refuses it (409) and `guard_owner_key()` (`20261026000400_owner_key_guard`) blocks it in the database. Forms show the slug, with that warning, only when adding or reviewing.
- Page keys are built by the database, never by code: the app sets the record's own slug (`artisan_sculpts.sculpt_id`, `keysets.slug`, `keyboards.slug`, from the name with `urlSlugify`) and the `update_maker_sculpt_id`, `update_profile_keyset_id`, and `update_brand_keyboard_slug` triggers (the first in `20260101000700_baseline_triggers`, the others in `20261021000100_page_renames`) join it to the parent (`maker_sculpt_id`, `profile_keyset_id`, `brand_keyboard_slug`). Children reference page keys with on update cascade, so renaming a page, or the maker, profile, or brand above it, moves them in the same statement. Writers that send only the key (catalog-sync's vendor adapters) still work: the trigger takes the slug from it. Children still send their parent's key as a reference (`maker_sculpt_id` on colorways, `profile_keyset_id` on kits).
- For insert, update, or patch payloads, use `pickTableFields(table, body)` from `server/utils/database.ts`. It validates that the body is an object and whitelists fields from generated metadata; generated columns (`fts`) are always dropped, so `omitSensitive()` is only for responses; its optional third argument lists columns clients must never write (`pickTableFields('keysets', body, ['profile_keyset_id'])`), such as the page keys and `source_slug` the database sets, instead of deleting or omitting them afterwards.
- Use `omitSensitive()` and existing response helpers when returning database records so internal fields such as `fts` are not exposed. It is shallow: strip nested embedded rows too (e.g. `colors.color` in `GET /api/keysets/[profile]/[keyset]`).
- Select only the columns a response uses when it is built from a few of them (e.g. `GET /api/search`, `GET /api/marketplace`, `GET /api/statistics`).
- Follow the existing pagination convention with `getQuery(event)` and Supabase `.range(from, to)`.
- Preserve existing full-text search behavior using Supabase `.textSearch()` where the endpoint already uses it.
- Public list reads of submittable tables filter with `PUBLISHED_FILTER` (`server/utils/index.ts`): `.or(PUBLISHED_FILTER)` after `.select()`, or with `referencedTable` for embedded rows. Never use `.neq('review_status', …)`, which also drops `null` rows. Current users: the sculpt and maker endpoints (colorways, counts, previews), colorway search, `GET /api/keysets`, the brand page's keyboards (and the releases and variants behind their covers), the search palette (keysets, keyboards, variants, and releases, which also need a published keyboard through `keyboards!inner`), `GET /api/statistics`, and the maker, profile, and brand lists (`GET /api/makers`, `/api/keysets/profiles`, `/api/keyboards/brands`) and their search palette groups. Those three lists take `?own=1` (`publishedOrOwnFilter`) to add the caller's own proposals, for the submission wizards only; detail endpoints of a maker, profile, or brand under review rely on RLS (404 for everyone but its submitter and staff).
- Artisan colorway search lives in `server/utils/colorway-search.ts` and matches published colorways (`PUBLISHED_FILTER`) by their own name only (every word of the term, `deleted` excluded); maker/sculpt-only matches are left to their own palette groups. `GET /api/search` (the `KeebSearch` palette) returns the 24 most relevant colorways (`searchPaletteColorways`: exact → prefix → phrase) with `total` and `viewAllTo`, and the palette appends a "View all N artisan colorways" row when `total` exceeds the shown items. `GET /api/search/colorways?q=&page=&size=&exact=` backs the `/artisan/search` results page, ordered by maker then sculpt (`size` capped at 72), returning `{ data, total }` and an empty page with the real total when `page` is past the end; `exact=1` keeps names containing the whole term as separate words (Postgres `imatch` with `\m`/`\M`, applied through `.filter()` because the client has no `imatch` helper). The page searches as the user types (400 ms debounce, `router.replace`), keeps `q`, `page`, `exact=1`, and `group=maker` in the URL, groups the current page by maker client-side, and offers Save to Collection for signed-in users. Other palette groups stay palette-only.
- Use `createError({ statusCode, statusMessage })` for expected API errors and match nearby status codes and messages.
- Do not expose service-role credentials or bypass authorization checks from client code.
- For submitter-owned records (e.g. `artisan_colorways.submitted_by`), grant the original submitter limited edit/delete rights in addition to staff permissions, scoped by the record's status (e.g. only while still `Pending`, or not once `Approved`). Always re-check ownership and status server-side; never trust a client-supplied owner id.
- Image uploads (`server/api/images/upload.post.ts`) require staff permission via `canManageAssignment`, except the `artisan`, `keyset`, and `keyboard` module categories, which any authenticated user may upload to (community submissions and edit suggestions); the underlying record save still enforces its own permission checks.
- For schema changes, draft an idempotent SQL migration under `supabase/migrations/` for the user to review and run in the Supabase SQL editor. `supabase/` is its own repository: commit there only when asked, following `supabase/AGENTS.md`.

## Cloudflare Worker Budget

Production runs on Cloudflare Workers (Workers Builds, Paid plan: CPU time is billed per request and capped by `limits.cpu_ms` in `wrangler.jsonc`; 128 MB of memory; Error 1102 when exceeded), so keep Worker work small:

- `routeRules` in `nuxt.config.ts`: `/about`, `/changelog`, `/privacy`, and `/why-choose-keebdex` are prerendered (served as static files); private pages and tools (`/account/**`, `/admin/**`, `/notifications`, `/recent-changes`, `/collection`, sort pages, submission pages, `/artisan/wishlist`, `/artisan/marketplace`, `/artisan/search`) are `ssr: false`. Public catalog pages keep SSR. Do not cache rendered HTML: it depends on the theme and color-mode cookies and the device. Add new private or list-heavy pages to the `ssr: false` group.
- Environment variables are listed in `.env.example`, each marked build or runtime. `nuxt.config.ts` runs only at build time, so `process.env` there bakes values into the bundle: never read secrets that way. Runtime values use `NUXT_` names matching `runtimeConfig` (`NUXT_CLOUDFLARE_*` for image uploads, `NUXT_APP_SECRET` for OG image URLs) and are set as Worker Secrets. The Cloudflare Images account hash (`runtimeConfig.public.cloudflare.accountHash`, not a secret: it is in every image URL) defaults to Keebdex's in `nuxt.config.ts` and is overridden by `NUXT_PUBLIC_CLOUDFLARE_ACCOUNT_HASH`; only resizing uses it, since image uploads take their URL (the `/public` variant) from Cloudflare's response. `NUXT_PUBLIC_SUPABASE_URL`/`_KEY` are needed at build time too (prerendering); a build without them deploys and then answers every request with a 500.
- `nitro.preset` is set to `cloudflare_module` on Cloudflare builds (`NITRO_PRESET` overrides it). Nitro would detect Workers Builds on its own, but nuxt-og-image reads the preset from the config and otherwise builds for `node-server`: OG images then fetch their fonts (`/_nuxt/fonts/*.woff2`) through Nitro, which serves no public assets on Workers, instead of the `ASSETS` binding, and fall back to a default font. Check OG image font changes on a Cloudflare build (`wrangler dev` on `.output/server/wrangler.json`), since the dev server loads fonts another way.
- Workers Builds deploys the `wrangler.json` that Nitro generates, replacing the Worker's dashboard settings. Bindings and settings (the `keebdex.org` custom domain, the D1 `DB` binding, also declared under `previews` so preview deployments get it, observability, placement, CPU limit, `keep_vars`) therefore live in the root `wrangler.jsonc`, which Nitro merges in; only Secrets survive from the dashboard.
- Keep SSR payloads small: trim with `pick`/`transform` in `useAsyncData` (e.g. `useKeysetProfiles`, the maker list) or select fewer columns on the server.
- Icons: `@nuxt/icon` bundles every icon named in `app/` and `content/` (`icon.clientBundle.scan`, shared by SSR) and loads any other (e.g. announcement icons from the database) from the Iconify API (`provider: 'iconify'`). Never switch back to the server provider: on Cloudflare it downloads and parses whole collections (solar is 11.7 MB) inside every new Worker isolate.
- `flag-icons` CSS is imported only by `MakerForm.vue` and `BrandForm.vue`, and its SVGs are emitted as files (`vite.build.assetsInlineLimit`); imported globally it added ~420 kB of inline CSS to every SSR response.

## State and Auth

Use the existing Pinia user store and composables before adding new global state. The user store (`app/stores/user.js`, plain JavaScript) holds `user`, `role`, `assignments`, `collections`, `favorites`, `social`, and `appearance`; `setCurrentUser()` runs after sign-in and `fetchUserPreferences(uid)` loads the profile row from `GET /api/users/:uid` (including appearance). `appearanceLoaded` distinguishes an empty server value from preferences that have not loaded; `saveAppearance(patch)` updates state immediately and debounces persistence by 500 ms. Sign-out calls `userStore.$reset()`; theme and color-mode cookies remain untouched. `app/composables/useSyncAppearance.ts` is invoked once from `app/app.vue` and owns server-to-client application, local seeding, change watching, and tab-focus refresh. Role/assignment rules (`admin`, `editor`, `maker`, `designer`) are centralized in `app/utils/permissions.ts` (`canManageAssignment`, `canManageAnyAssignment`). Assignments match a page exactly: a maker's `maker_id` covers its sculpts and colorways, a brand slug its keyboards, releases, and variants, and a keyset's `profile_keyset_id` (e.g. `gmk/olivia`, never the profile alone) the keyset, its kits, and its colors. `can_manage(scope)` mirrors this in the database. The rules are reused by both the client (`userStore.isEditable()`, `userStore.isModerator`) and server (`server/utils/admin.ts`). Do not reimplement role branching inline; extend or call the shared utility instead. Keep `app/middleware/auth.ts`, `app/middleware/admin.ts`, and server-side authorization checks aligned. Form components that need to know whether the current user is staff should read `useUserStore().isModerator` directly instead of accepting a `moderator` prop threaded down from the page — the prop is redundant since every call site already sourced it from the same store, and skipping it removes a layer of prop-drilling.

### Toast messages

Every toast has a short Title Case title (like HTTP status text: `Not Found`, `Session Expired`) and a full-sentence description. Build toasts with the helpers in `app/utils/toast.ts` (auto-imported) and pass the result to `useToast().add()`; do not hand-write success/error toast objects. `successToast(action, { entity, name, target })` covers record changes with a fixed set of actions: `add` (create, or add to a collection via `target`), `update`, `delete` (permanent), `remove` (take out of a collection), `move`, `approve`, `reject`; it renders a Title Case title (`Kit Added`) and a sentence description (`Kit "Base" has been added.`); pass `scope` for the parent of bulk results and `plural` for plural entity names that are not counted labels. Use `countLabel(n, 'kit')` as the `entity` for bulk results; the count appears only in the description (`3 kits in "GMK Olivia" have been approved.`), while the title drops it (`Kits Approved`). `notificationToast(view)` turns a rendered notification into a toast with a _View_ action. `noticeToast(key)` covers fixed app events that are not record changes (clipboard, sign-out, pins, sort order, feedback, `submission_pending`, `color_fetched`, `already_in_collection`); add a key there instead of an inline toast. `validationToast(message, title?)` is for client-side checks and shows the message verbatim as the description (default title `Invalid Input`); never route validation through `errorToast`. `errorToast(error, { showOriginalMessage })` is for caught errors: it logs and maps by status, and `showOriginalMessage` shows the server `statusMessage` as the description (use it where endpoints return user-facing messages, as the submission flows do).

Site-wide news lives in the database as announcements (see `docs/agents/announcements.md`), never as toasts written in code. The only hard-coded notice is the cookie consent (`useCookieConsent()`): `app/layouts/default.vue` adds the announcement toasts and then the consent on mount, through one `useToast()` instance (`showToasts(toast)`, `show(toast)`). The toaster measures each toast once on mount to lay out the stack, and every `useToast()` call has its own add queue, so toasts added through several instances can mount in the same tick, get measured at the collapsed height, and overlap when the stack expands; never reorder `toasts` either, since the toaster's ref order would no longer match. The app toaster is `{ max: 5, expand: false }` (`app/app.vue`). Tooltips open without delay app-wide (`UApp`'s `tooltip: { delayDuration: 0 }`), since they name icon-only buttons; don't set `delay-duration` per tooltip.

## Git and Documentation

Commit messages follow Conventional Commits through commitlint. Write user-facing notes for unreleased changes in `content/changelog/unreleased.md` (a bold-led summary paragraph, then What's New / Bug Fixes / Improvements; create the file with `title: Unreleased` frontmatter when it is missing); `CHANGELOG.md` only points there. To cut a release, run `bun run release <version> "<name>" [--prerelease]` (turns `unreleased.md` into `content/changelog/v<version>.md` with version, name, and date, keeps its `authors` or credits the `gh` user when it has none, and bumps `package.json`), commit it as `chore(release): v<version>`, push, then run `bun run release:publish <version>`, which creates the GitHub release (tag `<version>`, title `v<version> - <name>`, the format of every existing release) from that file, or updates it when it already exists. GitHub releases are copies of the files, never the source. Do not create commits, branches, or pull requests unless explicitly requested; writing the PR notes file described below is not a commit.

Release notes are read by collectors, not developers. Keep every release in the same shape:

- **Summary**: one short paragraph that opens with a bold phrase tied to the release name (e.g. "Throw the **doors open** —" for _Open Doors_), then names the two or three biggest changes.
- **Sections**, in this order and only when they have entries: `### ✨ What's New`, `### 🐛 Bug Fixes`, `### 🚀 Improvements`, then `### ⚠️ Breaking Changes` for changes users notice (renamed pages, moved addresses). Never write "None".
- **Entries**: a full, natural sentence each (two when needed), describing what users see or can now do and why it helps, in the present tense, ending with a period. Avoid clipped fragments that read abruptly ("Images load faster."); say enough to give context ("Grids load images sized for your screen, so pages load faster, especially on phones."). Bold the feature name when it leads the entry; italicize UI labels (_Save_, _Group Buys_).
- **Length**: there is no fixed number of entries; a big release can be long. What must not happen is overlap: merge entries that describe the same feature or area (e.g. several keyset page fixes) into one, and describe a large change once, in What's New, instead of again under Improvements.
- **Leave out** internal work users never see: composables, refactors, table or column names, lint and dependency updates, RLS or API fixes without a visible symptom. Do not list every label, route, or option; name the feature and its benefit.
- **Names**: release names are short and evocative, two or three words without a leading article, matching the theme of the release (_First Keystroke_, _Keyboard Era_, _Aurora Borealis_, _Open Doors_).
- **Authors**: keep `anhthang` first; add Claude as a co-author (`name: Claude`, `icon: simple-icons:claude`, `color: '#D97757'`, `to: https://claude.com/claude-code`) when Claude worked on the release.
- Before cutting a release, reread `unreleased.md` against these rules: entries added change by change tend to grow too long and to repeat each other.
